## 3. D2共用协议与文件改动边界

### 3.1 继续使用D1的四种记录

沿用原文的`IntentContract`、`AnswerEnvelope`、`Evidence`、`Step`，不另建管理数据库，不引入LangGraph、pgvector、GLiNER2或PP-StructureV3。[P3]

`AnswerEnvelope`顶层继续使用原有五种状态。新增细节优先放入已有字典或模块内部结构；修改公共协议必须A、B一起确认，并给旧输入提供默认值。

### 3.2 为①细化一份内部链接结果

以下为**建议的新增内部结构**，用于避免“只有一段改写文本，查不到绑定依据”。它不是替换公共协议。

| 字段 | 含义 |
|---|---|
| `mention_id`、`original_text`、`span` | 原始片段及字符范围，范围由后端统一解释 |
| `status` | `resolved / ambiguous / unmatched / error`，只在链接器内部使用 |
| `candidates` | 候选标准值及允许的字段绑定、来源记录、阶段分数 |
| `selected_candidate_id` | 已确定的候选；不确定时为空 |
| `match_method` | exact / pinyin / fuzzy / vector / llm |
| `evidence_ref` | 别名行、目录条目或值索引记录的标识 |
| `field_candidates` | 同一标准值可能出现于多个字段时，保留待定位的字段 |

例如，`Brazil`同时在不同表的国家列出现，不应只因重复出现就对“巴西有多少客户”反问；用“客户”这个明确查询对象约束到客户字段。业务对象本身未明确且字段会改变含义时，才保留歧义。

不要将内部`unmatched`直接映射成“问题不可回答”。明确给出的合法筛选值即使不在现有数据中，也可能正确返回0；原文的南极洲客户计数就是这种测试。[P7]

## 4. A线：把①接到现有NL2SQL里

### 4.1 D2-01：建立值索引、审核别名、拼音和向量

**改动文件：**沿用或实现`scripts/build_value_index.py`；写入`data/aliases/aliases.csv`，输出到`data/indexes/values/`。输出目录为本方案建议，不要求迁移D1已有目录。

**处理流程：**

1. 从D1已经核实的Chinook目录读取文本列。库名、表名和列名只从受信目录选择，不能接收用户随意拼接的SQL标识符。
2. 按原方案，对不同值数量小于5000的文本列建立值索引。可以读取最多5000个非NULL的不同值；达到5000则跳过完整索引，并记录原因，不声称已覆盖该列。
3. 保留数据库原始标准值，同时另存用于匹配的规范化表示。匹配时可处理大小写和多余空白，不能改写实际数据库值或破坏具有意义的符号。
4. 别名由模型起草、人工审核。原文四列“标准值、列、别名、来源”保留；建议附加`review_status`、`reviewer`。只有审核通过的行进入运行索引。
5. 为标准值及审核别名生成拼音和BGE-M3向量，记录同一模型配置、向量维度及记录顺序。直接复用D1的embedding适配器，避免A、B各加载一份大模型。
6. 生成构建审计：覆盖列数、值数、审核别名数、跳过项、失败项、向量矩阵形状及耗时。

pypinyin提供中文转拼音接口；RapidFuzz提供字符相似度及候选检索接口；BGE-M3提供稠密向量能力。D2采用这些现成能力，不新增抽取模型训练。[R2][R3][R4]

**建议的运行数据：**

```text
values.jsonl       # 标准值、字段、目录来源；不要混入题库答案
aliases.csv        # 原四列＋可选审核信息
pinyin_index.json  # 拼音 → 候选ID列表，保留同音冲突
embeddings.npy     # 与records顺序一致的归一化向量
records.jsonl      # 向量行对应哪个标准值／别名
index_meta.json    # 模型、维度、配置和输入摘要
```

这些属于索引构件，不是新增业务库。姓名、邮箱等数据不应无差别写进公开日志；使用权限沿用D1，前端与分享附件只展示本任务必要的脱敏摘要。

**验收：**已审核别名能返回正确候选；重跑不会重复累积；未审核别名不生效；同音多候选不会被字典覆盖；向量行数与记录数一致；失败列有记录。

### 4.2 D2-02：五级级联、受控改写与SQL硬约束

**改动文件：**`qa_agent/nlu/linker.py`、`rewrite.py`、`pipeline.py`以及既有SQL生成、校验模块。

#### 4.2.1 五级逐步尝试

原路线保持为：**别名精确匹配 → 拼音 → 字符模糊匹配 → 向量Top-5 → 必要时模型候选裁决**。[P2]

| 阶段 | 实施细化 | 禁止的捷径 |
|---|---|---|
| 精确 | 标准值和审核别名都作为入口；结合查询对象筛选字段范围 | 同名出现多列时随便选第一列 |
| 拼音 | 比较审核中文名称的拼音；保留同音候选 | 拼音一致即认定必然是同一对象 |
| 模糊 | 对候选使用同一种明确的字符评分，记录前两名和差距 | 用同一阈值混合拼音、字符分数和余弦分数 |
| 向量 | 同一embedding配置编码查询片段，取Top-5候选 | 将召回到的第一名等同事实 |
| 模型裁决 | 只给合法候选ID、字段语义和用户上下文；允许返回未确定 | 返回候选集合之外的对象，或自报概率后直接放行 |

阶段分数是匹配分，不是“正确概率”。原方案未给固定阈值，本文件不伪造最优数值；放到配置中，只使用开发集调整并记录配置。语义上有多个合理解释时，不得靠调高分数把歧义隐藏掉。

同一请求中的未确定片段可合并给模型判断，避免对每个候选各调用一次；这是本方案建议的成本控制。

#### 4.2.2 D2先处理不确定性，不抢做D3全套澄清

已确认绑定进入SQL；多个合理候选写入`intent.unresolved`，利用原`NEEDS_CLARIFICATION`状态显示一个简单问题和选项。若D1没有恢复机制，D2允许用户用明确说法重新提问，并标为“最低限度歧义拦截”。完整L0/L1/L2状态机及多轮补丁仍属于D3。

D2不确定或失败时不能静默挑第一名。模型超时属于技术失败，不伪装成用户歧义。

#### 4.2.3 改写只作用于已核验片段

保存原问题。每处改写都包含原字符范围、替换文本和依据；校验范围匹配且不重叠后，从后向前应用补丁，避免前面的替换使后续位置错位。

示例：`巴稀的客户有哪些` → `巴西的客户有哪些`，并单独输出`customer.country = Brazil`的绑定。

“客护→客户”等业务词纠错必须有目录或审核术语映射作为依据，不能把它冒充为国家值索引的功劳。不能增加用户没说的时间、Top-N或金额口径。

#### 4.2.4 SQL约束不能只靠一句提示词

生成器接收当前意图、目录和已核验的字段／值绑定；参数值优先走现有数据库驱动的参数机制。生成后，用SQLGlot解析结构，核对筛选字段、操作符及值是否满足绑定，识别表别名，不使用全局字符串替换。[R5]

SQLGlot仅提供结构处理基础，绑定语义检查由本项目实现。继续保留D1的只读账户、语句数量限制、超时和目录权限。建议同时检查子查询中的危险操作，不能只检查根节点看起来像SELECT就通过。

校验或执行失败按原方案有限修复，修复必须保留用户条件和有效绑定。不要借“修复”偷偷删除筛选条件；空结果不应触发换国家或换年份。

**最低验收例子：**

| 输入类型 | 预期 |
|---|---|
| 清晰标准问题 | 与D1正确结果一致，不增加无谓追问 |
| `巴稀`／`老美`／英文拼写变体 | 有实际存在的候选和可追溯绑定 |
| `Rock`与`Rock And Roll`的真实歧义 | 保留候选，不静默合并 |
| 合法但没有记录的国家筛选 | 可正确返回0／无记录，不改成近似国家 |
| 生成SQL故意使用错误标准值的单测 | 绑定核验阻止执行 |
| 同一片段出现两次／中英混合标点 | 补丁不越界、不修改无关位置 |

所有示例对象都要先在实际D1快照中核查。确定性单测可以使用受控假数据或模拟模型，但实际链路验收必须标明是否真实调用了模型和数据库。

**防泄漏规则：**

- 总量50和30表示完成题库建设，不表示D2要运行全部题。
- 原文要求约30%保留到D5。常规目标为单表35开发／15保留，鲁棒21开发／9保留；鲁棒变体和原题必须同组。
- D1已经运行或用于调参的题只进入开发集。单表题可以保留D1已用30题，再从新增20题中选5开发、15保留。
- 先确定同源分组再选择鲁棒变体，不能为了凑数量把同源题拆到不同组。
- 题库答案、gold SQL和保留题不进入别名生成、业务目录、检索索引或运行提示词；冻结后保留集由评测程序解封。

EX原口径保留：忽略列名及列顺序、数值按原文保留2位小数，要求排序时比较行序，否则比较多重集合，执行失败、超时和误澄清均计错。[P5]

**实施细化：**“忽略列顺序”不等于独立排序每行单元格，应使用固定的一对一列对应再比较整行；无序结果仍保留重复行数量。不要改变原评价规则，只应把其程序含义写清。主键、计数仍保留精确类型；百分比、单位及多个数值列的含义需人工核对并单列错误，不能被统一小数格式掩盖。

### 4.4 D2-04：错误分析、回归与85%检查点

先保存D1共同开发题的基线，再运行D2同题结果。新增题另列，不能把D1的30题准确率与D2不同的35题准确率直接当作模块提升。

沿原方案按`value_link / schema / sql_logic / clarify_wrong / retrieval_miss / unfaithful / format / timeout`记录错误；D2 A线优先修前三类。[P5]

| 错误 | 首先修改 | 证据 |
|---|---|---|
| 列描述错误或含义不清 | 目录描述、日期／金额口径 | 对应目录差异、同题回归 |
| 值绑定错误 | 别名审核、候选召回、字段范围、决策规则 | 片段、候选、分数、绑定前后 |
| SQL逻辑错误 | 生成约束、结构校验、必要的提示词 | 旧SQL、新SQL及结果 |
| 输出／网络错误 | 既有适配器的格式校验、超时、有限重试 | 错误类型、次数，不泄露密钥 |

若开发集是35题，至少30题正确才能达到85%检查点（30/35≈85.71%）；报告同时写“正确数／实际题数”，不能只报百分比。

本日建议在开发集做一次①开／关的对照作为证据；这属于细化，不要求D2就完成D4计划的全套消融。开关仅关闭链接增强，不能关闭SQL安全校验；每组使用相同问题、快照和模型配置，不复用另一组缓存答案。

### 5.2 D2-06：混合检索、引用与数字核验

**文件：**`rag/index.py`、`retriever.py`、`answer.py`；可以在现有文件中实现核验函数，不要求新增框架。

#### 5.2.1 两路检索使用同一批片段

BM25和BGE-M3都索引同一份`chunk_id`列表。文档与查询采用一致分词／规范化；`rank_bm25`本身不替你完成分词和预处理。[R7]

用户选定单文档时，先限定可参与检索的`doc_id`，再做两路排名；不能先全库取Top-K再简单删除其他文档，导致本应命中的片段被挤掉。

向量索引与查询向量必须使用相同模型配置、维度和归一化。模型配置改变时重建值索引和文档索引；不混用新旧向量。启动时检查矩阵行数与片段列表一致。

#### 5.2.2 用RRF融合排名，不相加两种原始分数

原方案指定RRF，以下将其落成可配置步骤：两路各取Top-20作为初始候选（不足20则用实际数量），对相同`chunk_id`累加排名贡献，再取Top-8给模型。Top-20是本方案的起始建议，Top-8来自原文。[P3]

公式为：

`RRF(chunk) = Σ[1 / (k + rank(chunk))]`

只对召回该片段的列表求和；名次从1开始；初始`k=60`，相同分数用稳定的`chunk_id`排序。RRF原论文提出按排名融合；这里不训练新模型，也不声称60在本数据上最优。[R8]

保存BM25、向量、融合后三份排名。Hit@5只看最终排名前5，不能因为生成用了8段就把第8段命中也算Hit@5。

#### 5.2.3 回答只引用本次真实给到的证据

把最终证据编号交给模型，要求输出答案和引用。编号由程序分配，并能映射到真实`chunk_id`、文档和位置；不能用模型自己编的文件名与页码。

生成后检查：引用ID均存在；有事实陈述却无引用时标出；答案中的数字能在它所引用的片段内核对；用户指定文档时引用不得越界。

数字检查只允许无歧义的展示规范化，例如全角与半角、千分位和多余空格；不要把0.15与15%、不同币种、不同年份或负数正数直接视为同一个量。编号如`[E2]`、列表序号与页码标签不计作答案事实数字。

**同一个数字在片段中出现，不代表陈述就一定正确。**对象、期间和单位可能不对应，因此保留原计划的人工忠实度复核；机器核验只作低成本拦截。

失败时带核验原因重生成一次；仍失败就明确标出未核实内容，不能伪装为已通过。证据不足按D1既有语义返回说明；若需统一为`UNSUPPORTED`，须在协议记录中写清是“当前资料不支持”。网络错误仍为`FAILED`，不让用户替工具故障补条件。

**单测：**不存在的引用ID、数字来自另一条未引用证据、百分号／负号错误、同名文档越界、空检索结果，以及一次重生成后仍失败。

## 8. 日终联调与检查点

### 8.1 最少联调场景

| 场景 | 需要看到的证据 |
|---|---|
| 明确的单表计数题 | 原输入、有效SQL、真实结果、无不必要澄清 |
| 原题和别名／错字变体 | 相同业务条件与结果、不同的链接步骤和改写证据 |
| 未知但合法筛选值 | 不强行改成相似值；0或无记录被如实显示 |
| 多候选歧义 | 停止无依据查询；未确定项可见 |
| 指定文档的文本问题 | 检索不越界，引用ID与页面／章节相符 |
| 一道图像／扫描文档问题 | 有真实OCR输出和位置；识别失败就如实失败 |
| 证据不足问题 | 不利用模型记忆编造答案 |
| 引用ID／数字不合法的测试 | 校验失败、有限重试及最终状态可查 |

这是联调场景集，不替代九项任务验收，也不把D3完整多轮能力提前宣称为已实现。

### 8.2 日终报告必须包含

D1共同题基线、D2共同题结果、新增开发题结果；各题库总数／开发数／保留数／实际运行数；正确数和分母；RAG可回答题与证据不足题的分别结果；典型错误与修复；代码提交标识、配置和数据范围；实际模型调用与模拟调用的区分；未完成项。

没有运行保留集就写“D5待测”，不能写0%也不能复制开发集成绩。报告输出`eval/reports/d2.md`，不要覆盖D1原验收文档，也不要提前命名为`final.md`。

### 8.3 未达标怎么处理

原方案D2晚检查EX≥85%和RAG是否能带引用回答；不达标时，D3上午继续修基础，AdventureWorks工作后移，并削减④的可选剪枝步骤。[P9]

当天没有跑通的第五级链接、某种解析器或13份样本要明确标成部分完成，不通过删失败题、改gold、用未审核别名或虚构截图补齐。延迟过高先看真实trace，不未经测试断言全部耗时来自模型。
