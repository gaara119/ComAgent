## 1 我们对赛题的理解

### 1.1 赛题到底要什么

一句话：做一个智能体。它能听懂业务人员的日常说法，自己决定查库还是查文档，查得准，还能把每一步的证据摆出来。

评审看重的是**精准**和**可解释**，不是模型多大、组件多全。所以系统的主张是：

> **大模型负责理解和组织语言；确定性工具（SQL 校验器、只读数据库、检索器、规则表）负责事实和执行；每一步都留痕并展示。**

这和现有方案（尤其是 03）的核心思想一致，保留。

### 1.2 初赛评分拆解（赛题第 10–11 页）

| 大项 | 内容 | 满分 | 拿分条件 | 依赖可运行系统 | 目标 |
|---|---|---|---|---|---|
| 功能 | 基础 NL2SQL 单表 | 10 | ≥10 个用例，每正确执行 1 分 | 是 | 10 |
| 功能 | 基础 RAG 单文档 | 10 | ≥10 个用例，每正确 1 分 | 是 | 10 |
| 功能 | 答案可解释性 | 5 | 有展示得 3，质量高得 5 | 是 | 5 |
| 功能 | Demo 可用性 | 5 | 可用得 3，体验好得 5 | 是 | 5 |
| 性能 | NL2SQL 执行准确率 | 10 | 准确率 ≥70/80/90% → 6/8/10 分 | 是 | 10 |
| 性能 | RAG 答案忠实度 | 10 | 准确率 ≥70/80/90% → 6/8/10 分 | 是 | 8–10 |
| 性能 | 系统效率设计证明 | 5 | 复杂度分析 + ≥2 种规模实测或预估 + 瓶颈与优化 | 部分 | 5 |
| 优化 | 中级任务数量与质量 | 15 | 每项 5 分，上限 15 | 是 | 15 |
| 优化 | 鲁棒性（模糊输入、错别字） | 10 | 基础 5，良好 7，优异 10 | 是 | 7–10 |
| 优化 | 多轮对话 | 5 | 有多轮得 3，连续 5 轮以上准确得 5 | 是 | 5 |
| 文档 | 完整性、规范性、可读性 | 10 | 6 / 8 / 10（工业文档水准） | 否 | 8–10 |
| 演示 | 演示视频或截图 | 5 | 清晰展示核心功能 | 是 | 5 |

结论：

- **85 分直接依赖可运行系统**。纯文档只能拿文档质量 10 分，以及效率证明的一部分。
- 硬门槛：作品必须**至少完成 1 个中级任务**才算有效（第 11 页）。

### 1.3 初赛提交物（赛题第 8–9 页）

1. **设计报告**：Word 和 PDF 各一份，建议不超过 20 页（含封面、目录、附录）。
   - 封面或目录后的第 1–2 页必须是**“项目核心亮点预览页”**。
   - 亮点页要包含：系统整体架构图、多模态数据融合处理链路、核心创新点摘要、已攻克中级任务清单。
   - 还要给出**关键数据**，如 NL2SQL 执行准确率、RAG 检索命中率、澄清交互成功率。
2. **技术实现说明书**：Word 和 PDF 各一份，建议不超过 30 页，必须覆盖 7 块：
   1. 系统总体架构
   2. NL2SQL（Schema Linking、要素识别模型、SQL 生成与校验）
   3. RAG（解析与切片、向量检索、生成融合）
   4. **多源异构数据融合推理策略**
   5. 可解释性（推理链路追踪、来源标注、工具调用链可视化）
   6. 中级任务攻克详述
   7. 系统测试与性能评估
3. **技术数据 ZIP**，包含：
   - 完整源码，含目录说明和 README
   - 数据库 schema 定义文件
   - **知识库文档样本 ≥10 份，且覆盖不同格式**
   - 模型权重（若适用）
   - 运行环境说明，含依赖包及版本号
   - **快速启动脚本**
4. **演示**：视频或截图，对应“演示效果”5 分。

### 1.4 容易漏掉的 6 个点

1. **评委可能用自己的题测**。“采用至少 10 个测试用例进行客观评估”没说用谁的题。系统必须对**没见过的简单中文问题**也稳定，所以内部题库要 50 道以上，类型覆盖全。
2. **不该澄清时别澄清**。基础单表题如果系统反问一句，评委可能直接判错。所以澄清要分级，见 §3.6.4 的 L0 / L1 / L2。
3. **亮点预览页要数字**。没有评测脚本就没有数字，D1 就要把评测脚本建起来。
4. **“多源融合推理策略”是说明书的必写章节**。现有方案把跨源推迟到了第二版；初赛至少要有 2 类能跑的跨源问题。
5. **效率测试要 ≥2 种数据规模**。Chinook 的 `invoice_line` 只有约 2 千行，需要做标注清楚的扩容副本（§5.5）。
6. **知识库 ≥10 份，且覆盖不同格式**。同一份文档转三种格式不算（00 方案里也写了这一点），要真有 PDF、扫描件、HTML、DOCX、Markdown、图片等不同的文档。

## 2 现有方案诊断

### 2.1 值得保留的

- **核心原则**：模型提出理解，程序校验并执行。答案和证据一起产生，不事后补写 SQL 或引用。
- **区分两类“不知道”**：用户意图不明确，和系统能力不足，要分开处理（03 §2）。
- **统一协议**：IntentContract（意图记录）和 AnswerEnvelope（答案加证据）。用户改了条件，相关下游结果要失效（03 §4.8）。
- **数据纪律**：测试答案不进运行库；派生数据要标注；不虚构跨源关联。
- **03 的澄清原则**：能自己查证的先查证，只有需要用户做业务选择时才问。这是 ③ 的卖点。

| ④ 精准表定位 | 必做 | AdventureWorks 68 表 |
| 跨源融合 | 做 2 类 | 说明书必写章节 |
| ② 可扩展要素提取 | 备胎 | 复用 ① 的抽取器，加一个新领域配置演示 |
| ⑤⑥⑦⑧⑨ | 留给决赛 | |

为什么选 ③①④：

- **③**：
  - 你们自己的设计最完整。
  - 多轮对话 5 分基本靠它；亮点页点名要“澄清交互成功率”。
  - 决赛“智能意图理解与澄清”的 10 分也是它。
- **①**：
  - Chinook 的数据值全是英文（国家是 `USA`，流派是 `Rock`），评委多半用中文提问。“美国→USA”“摇滚→Rock”本身就是要素链接问题。
  - 所以 ① 同时提升 NL2SQL 准确率和鲁棒性（错别字、别名、拼音）。
- **④**：决赛要求 ≥3 个中级任务，还要考复杂 NL2SQL 准确率。④ 现在做，决赛直接复用。

### 3.2 简化后的架构

```
  Streamlit 前端（聊天 / 澄清卡片 / 链路面板 / 评测看板）
  FastAPI（/api/chat：供 API 交互和评测脚本调用）
                │
                ▼
用户问题 ──► NLU（1 次 LLM 调用）：路由 + 任务类型 + 要素片段 + 意图补丁
                │
                ├─► ① 要素链接：别名表 → 拼音 → 模糊匹配 → 向量召回 →（必要时）LLM 裁决
                │      输出：标准值绑定 + 改写后的问题（界面展示改写差异和依据）
                │
                ├─► ③ 校验与澄清：规则表检查缺失 / 歧义 / 冲突
                │      L0 直接执行 / L1 按默认执行并声明 / L2 出澄清卡片
                │      会话状态：IntentContract（带 intent_version），多轮补丁与失效
                │
                ├─► 路由
                │    ├─ SQL 通道：④ 表定位 → SQL 生成 → SQLGlot 校验 → 只读执行 → 有限修复
                │    ├─ 文档通道：混合检索（BM25 + BGE-M3，RRF 融合）→ 带编号证据生成 → 引用与数字核验
                │    └─ 跨源通道：两步计划（SQL→文档 / 文档→SQL），步骤之间传结果
                ▼
AnswerEnvelope：答案 + 结果表 + SQL + 引用片段（文档 / 页码 / 高亮）
                + 链路步骤（每步输入输出与耗时）+ 声明的假设
```

| 12 | 《Chinook 业务指标口径手册》 | DOCX | 团队编写，明确标注“项目自编” | 跨源：文档→SQL；也是 ③ 的口径依据 |
| 13 | 《Chinook 数据字典（中文）》 | Markdown | 团队编写 | ① 的别名来源、④ 的列描述 |

说明：

- **OHR 的 QA 字段**：`doc_name, ID, questions, answers, doc_type, answer_form, evidence_source, evidence_context, evidence_page_no`。挑 `evidence_source = text` 的题做单文档 RAG 测试。`answers` 和 `evidence_context` 只放在评测侧，不进检索库。
- **语言**：先盘点 OHR 文档的语言。中文问答主要靠第 8–13 份文档补足。
- **艺术家百科是真实关联**：Chinook 的 artist 表本来就是真实乐队，不是虚构的员工或企业。这符合现有方案“跨源关联必须真实可核验”的原则，也正好对应赛题第 4 页“销售冠军 + 成功方法论”的例子。如果访问不了维基百科，换成其他允许引用的公开介绍，注明来源即可。
- **口径手册**：定义“销售额、客单价、复购客户、热门曲目”等指标的计算方式。企业里确实有这类文档，这里作为“项目自编规则文档”使用，不冒充外部事实。

#### 3.4.3 跨源问题（初赛做 2 类，决赛扩到 ≥5 类）

| 类型 | 例子 | 执行步骤 |
|---|---|---|
| SQL→文档 | “销售额最高的艺术家是谁？介绍一下他们的音乐风格。” | ① SQL 求销售额第一的艺术家；② 用艺术家名过滤知识库并检索；③ 合成答案，同时展示 SQL 和引用 |
| 文档→SQL | “按口径手册里‘客单价’的定义，算一下美国客户某年的客单价。” | ① 检索口径手册里“客单价”的定义；② 在目录约束下把定义转成 SQL 表达式；③ 执行；④ 答案同时引用手册和 SQL |
| （选做）对比 | “Iron Maiden 在曲库里有几张专辑？和百科记载的录音室专辑数一致吗？” | SQL 计数 + 文档抽取 + 比较 |

### 3.5 最小数据协议（D1 两人一起定，之后不随便改）

```python
# qa_agent/schemas.py（示意，用 pydantic）
class Step(BaseModel):            # 链路中的一步，既用于可解释展示，也用于效率统计
    name: str                     # nlu / link / clarify_check / schema_link / sql_gen / sql_validate / sql_exec / retrieve / answer
    status: Literal["ok", "warn", "error", "skipped"]
    input_summary: dict
    output_summary: dict
    latency_ms: int

class Evidence(BaseModel):
    evidence_id: str              # 由程序生成，模型只能引用已有的 id
    doc_id: str
    doc_title: str
    page: int | None              # 物理页，从 0 开始；展示时 +1
    section_path: list[str]       # 章节路径
    text: str
    bbox: list[float] | None

class IntentContract(BaseModel):
    intent_version: int
    route: Literal["sql", "doc", "hybrid", "chitchat"]
    task_type: str                # lookup / aggregate / ranking / growth / ratio / doc_qa ...
    metric: str | None
    time_scope: dict | None
    filters: list[dict]           # 每项含值、绑定的 table.column、来源（用户 / 链接 / 默认）
    grouping: list[str]
    order: dict | None
    assumptions: list[str]        # L1 默认口径的声明
    unresolved: list[dict]        # 待澄清的问题

class AnswerEnvelope(BaseModel):
    trace_id: str
    status: Literal["SUCCEEDED", "EMPTY_RESULT", "NEEDS_CLARIFICATION", "UNSUPPORTED", "FAILED"]
    answer: str
    rewritten_question: str | None
    sql: str | None
    table: list[dict] | None
    evidences: list[Evidence]
    clarification: dict | None    # {question, options: [{id, label}], allow_free_text}
    intent: IntentContract | None
    steps: list[Step]
```

`Step` 由一个 `@traced("sql_exec")` 装饰器自动记录。这样**可解释性面板和效率统计用的是同一份数据**，不需要另外埋点。

### 3.6 各模块设计要点

#### 3.6.1 NLU 与路由（1 次 LLM 调用）

一次调用同时输出：

- 路由和任务类型；
- 要素片段（类型不预设）；
- 指标、时间、分组、排序；
- 多轮场景下，相对上一轮意图的**补丁**。

少一次调用，就少一两秒延迟。输出示例：

```json
{"route": "sql", "task_type": "aggregate",
 "mentions": [{"text": "巴稀", "type_guess": "国家", "role": "filter"}],
 "metric": "客户数", "time_scope": null, "grouping": [], "order": null,
 "is_followup": false, "patch": []}
```

路由规则（按优先级）：

1. 用户在界面上选定的范围优先。
2. 能链接到库中的值或列 → `sql`。
3. 问的是“介绍、为什么、规定、方法、文档里怎么说” → `doc`。
4. 两类都有 → `hybrid`。

#### 3.6.2 基础 NL2SQL 链路

1. **目录**：
   - 从 `information_schema` 和外键约束自动导出表结构。
   - 给每张表、每一列补中文描述和示例值：LLM 生成初稿，人工过一遍，存到 `data/catalog/chinook.yaml`。
   - Prompt 里用“表名(中文描述) / 列名 类型 中文描述 示例值”的紧凑格式（参考 XiYan-SQL 的 M-Schema 写法）。
2. **生成**：
   - 输入：改写后的问题、④ 给出的子 schema、已声明的假设。
   - ① 的值绑定作为硬约束传入，例如“筛选国家必须用 `'Brazil'`”。
   - 输出 JSON：`{sql, tables_used, explanation}`。
3. **校验（SQLGlot）**：
   - 只允许一条语句，根节点必须是 SELECT / WITH / UNION。
   - 用到的表和列必须在目录里。
   - 禁止危险函数，如 `pg_sleep`、`dblink`、`COPY`。
   - 非聚合查询没有 LIMIT 时，补上 `LIMIT 200`。
4. **执行**：用只读账号 `qa_reader`，设置 `default_transaction_read_only = on` 和 `statement_timeout = 5s`。
5. **修复**：
   - 数据库报错：把错误信息和 SQL 交回模型修改，最多 2 次。
   - 空结果：先检查值绑定（大小写、空格），重试 1 次；仍为空就如实返回 `EMPTY_RESULT`，不擅自换条件。
6. **答案**：单个数值用模板直接回答，省一次 LLM 调用；结果是表格时，才让 LLM 写一两句总结。
7. **可选提准**：准确率卡在 85–90% 时，对低置信度的题生成 3 条候选 SQL，执行后按结果多数投票。先在评测集上量化收益，再决定要不要默认开启。

#### 3.6.3 ① 要素精准识别与问题改写

**目标**：任何类型的要素（国家、城市、流派、艺术家、媒体类型……类型不预设）都能从不标准的说法映射到库里的标准值，再据此改写问题。

**离线准备**

- **值索引**：扫描所有低基数文本列（不同值少于 5000 个）的 DISTINCT 值，记为 `(table.column, value)`。
- **别名表 `aliases.csv`**：
  - 字段：`标准值, 列, 别名, 来源`。
  - 国家、流派、媒体类型和头部艺术家的中文名及常见别名，由 LLM 批量生成初稿，再人工审核。
  - 例如：`USA ← 美国 / 美利坚 / 老美 / US`；`United Kingdom ← 英国 / UK / 大不列颠`；`Rock ← 摇滚`；`Heavy Metal ← 重金属`。
- **拼音和向量**：为每个标准值和别名计算拼音（pypinyin）和向量（BGE-M3）。

**在线级联**：每个要素片段依次尝试下面几级，命中高置信度就停。

| 级 | 方法 | 解决的问题 | 例子 |
|---|---|---|---|
| 1 | 别名精确匹配 | 别名、黑话 | 老美 → USA |
| 2 | 拼音匹配 | 同音错别字 | 巴稀 → 巴西 → Brazil |
| 3 | 字符模糊匹配（rapidfuzz） | 英文拼写错误 | Metalica → Metallica；Brasil → Brazil |
| 4 | 向量召回 Top-5 | 没登记过的说法 | “南美那个足球很厉害的国家” → 候选 |
| 5 | LLM 在候选中裁决 | 多候选消歧 | 摇滚 → Rock / Rock And Roll |

**决策**：

- Top1 得分高，且明显领先第二名 → 直接绑定。
- 多个候选得分接近 → 交给 ③ 处理（L1 按默认执行并声明，或 L2 澄清）。
- 一个都不像 → 保留原词，标记为“未知要素”。

**改写**：只做补丁式改写，不自由扩写。界面展示改写差异和每处修改的依据，例如：

- 原问题：`巴稀的客护有那些`
- 改写后：`巴西（customer.country = 'Brazil'）的客户有哪些`
- 依据：`巴稀 → 巴西`（拼音匹配 0.97）

**和 ② 的关系**：给新领域（AdventureWorks）接入要素识别时，只需注册值索引和别名表、补类型说明，代码不用改。D4 如果有余力，录一段“5 分钟给 AW 接入要素识别”的演示，② 就有了实证。

#### 3.6.4 ③ 智能语义校验与澄清（在 03 基础上的改动）

**新增：澄清分级**，解决“该不该问”。

| 级别 | 条件 | 系统行为 | 例子 |
|---|---|---|---|
| L0 | 必要条件齐全，没有歧义 | 直接执行 | “巴西有多少客户” |
| L1 | 有歧义，但有登记过的默认口径，且不是比较类任务 | 按默认口径执行，答案顶部声明假设，并给“切换口径”按钮 | “最受欢迎的 5 首歌”：默认按购买数量，可切换为按销售额或按歌单收录次数 |
| L2 | 必要条件缺失且没有合理默认；或不同口径会导致结论明显不同；或是增长率、同比、占比这类比较任务 | 暂停，弹出澄清卡片 | “美国销售额同比增长多少”（缺年份）；“摇滚歌曲有多少”（Rock / Rock And Roll，数量差别大） |

L1 的“一键切换”是一种低成本的澄清：既不打断简单问题，又能展示澄清能力。

**规则表 `clarify_rules.yaml`**：跨领域复用，换领域只改绑定。

```yaml
task_types:
  growth:        # 同比 / 环比 / 增长率 / 增幅
    required: [metric, time_scope.current, comparison.type]
    derivable: {time_scope.base: "由 current 和 comparison.type 推导"}
    level_if_missing: L2
  ratio:
    required: [numerator, denominator]
    level_if_missing: L2
  ranking:
    required: [metric, rank_object]
    defaults: {top_n: 10}
ambiguities:
  - id: popularity
    trigger: ["最受欢迎", "最热门", "卖得最好"]
    level: L1
    default: by_quantity
    options:
      - {id: by_quantity, label: "按购买数量", expr: "SUM(invoice_line.quantity)"}
      - {id: by_revenue,  label: "按销售额",   expr: "SUM(invoice_line.unit_price * invoice_line.quantity)"}
      - {id: by_playlist, label: "按被收录的歌单数", expr: "COUNT(playlist_track.playlist_id)"}
  - id: multi_candidate_value     # 来自 ① 的多个候选
    level: L2
    options: from_linker
```

**澄清卡片**包含：

- 问题和一句原因；
- 选项：来自目录或数据，例如可选年份来自 `SELECT DISTINCT EXTRACT(YEAR FROM invoice_date)`；
- 一个自由输入框。

选项都带稳定 id，用户点击后不需要再让模型解析。

**多轮状态**：

1. 每个会话保存当前的 `IntentContract`。
2. 用户每说一句，NLU 输出补丁（`set / add / remove`）。
3. 程序应用补丁，`intent_version + 1`。
4. 按依赖表让受影响的部分失效（沿用 03 §4.8 的表：改地区只重算结果；改指标要重新检查粒度、聚合和字段）。

**实现**：

- 写一个约 200 行的状态机：`IDLE → CHECKING →（WAITING_CLARIFICATION）→ EXECUTING → ANSWERED`。
- 会话存在内存字典里，同时落盘成 JSON。
- 前端提交澄清回答时带上 `clarification_id` 和 `intent_version`，防止用户在旧卡片上点选，改到了新任务。

**03 文档本身要改的地方**：

- 删除第 31 行“多智能体 gpt 说……”这条备注。
- 补上目录里列了、正文却缺失的第 6 章“参考资料”。
- 第 5 章补上指标定义（§5.2）。
- 把 LangGraph 改为“自写状态机，接口可平滑迁移到 LangGraph interrupt”。
- 把演示例子换成：同比缺年份、热门口径、摇滚多候选。

#### 3.6.5 ④ 精准表定位（AdventureWorks）

1. **目录构建**（离线）：
   - 自动导出 68 张表的列、类型和主外键。
   - 让 LLM 根据表名、列名和示例行，为每张表生成中文描述（约 68 次调用），人工抽查。
2. **双路召回**：
   - 问题和要素 → 表描述向量，取 Top-8。
   - 问题和要素 → 列描述向量，取 Top-20，再投票到所属的表。
   - ① 的值索引命中的列，也加入候选。
   - 三路结果用 RRF 合并。
3. **外键图补全**：
   - 用 networkx 建外键图，对候选表求 Steiner 树近似（`networkx.algorithms.approximation.steiner_tree`）。
   - 这样会自动补上桥接表，例如 `salesorderdetail → product → productsubcategory → productcategory`。
4. **LLM 剪枝**：
   - 把不超过 12 张候选表的描述和列交给模型，让它选出必需的表和列，并写出理由。
   - 程序检查剪枝后是否仍然连通；不连通就把桥接表加回来。
5. **输出 SchemaBundle**，包括：
   - 选中的表和列；
   - JOIN 路径（外键对）；
   - 每张表的入选理由；
   - 被排除的近似表及排除理由。

   界面里展示“为什么选这些表”。
6. **干扰项例子**（演示用）：
   - `sales.salesorderheader` vs `purchasing.purchaseorderheader`（销售单 vs 采购单）
   - `humanresources.employee` vs `sales.salesperson`
   - `person.address` vs `sales.customer`
7. **评测**：
   - 30 道 AW 题，标注 gold 表，计算表召回率、精确率和平均候选表数。
   - **消融**：全量 schema 直接交给模型 vs 只给 ④ 选出的子图，比较执行准确率和 prompt token 数。这就是“攻克质量”的证据。

#### 3.6.6 单文档 RAG

- **解析**：

  | 格式 | 工具 | 保留的信息 |
  |---|---|---|
  | PDF | PyMuPDF `get_text("dict")` | 页号、bbox、字号（用字号粗略识别标题） |
  | DOCX | python-docx | Heading 样式 |
  | HTML | BeautifulSoup | h1–h3 和段落 |
  | Markdown | 按 `#` 切分 | 标题层级 |
  | 图片、扫描页 | RapidOCR | 文字和位置 |

- **切片**：
  - 先按标题分节，节内按 400–600 字切，重叠 80 字。
  - 每片带 `doc_id`、章节路径、页号和 bbox。
  - 向量化时，在正文前拼上“《文档名》> 章 > 节”。
- **检索**：
  - BM25（jieba 分词）加 BGE-M3 向量，用 RRF 融合后取 Top-8。
  - 单文档模式下，在检索阶段就按 `doc_id` 过滤。
- **生成**：
  - 证据按 `[E1]…[E8]` 编号放进 prompt，要求每句话都标引用。
  - 证据不够时，回答“文档未提供足够依据”。
  - 输出 `{answer, citations}`。
- **核验**（低成本的忠实度保护）：
  - 引用的 id 必须在给出的证据里。
  - 答案里出现的数字，必须能在被引用的片段里找到。否则重新生成一次；仍不通过就标注“未核实”。
- **展示**：
  - 引用片段、文档名、页码。
  - PDF 证据可以用 PyMuPDF 渲染该页并画出 bbox 高亮。这一项优先级 P2，有时间就做，对可解释性加分明显。

#### 3.6.7 可解释性展示

每条回答下方有三个折叠面板：

1. **推理链路**：步骤时间线。每步都可以展开，查看输入输出 JSON。例如：

   ```
   意图理解 0.9s
   → 要素链接：巴稀 → Brazil（拼音匹配 0.97）
   → 澄清检查：通过（L0）
   → 表定位：customer（附理由）
   → SQL 生成
   → 校验 ✓ 只读 ✓
   → 执行 12ms，返回 5 行
   → 回答
   ```

2. **SQL 与结果**：语法高亮的 SQL、结果表、数据库名。
3. **引用来源**：片段原文、文档名、页码、高亮。

此外还展示问题改写差异、L1 声明的假设，以及多轮对话时的当前条件摘要。

链路面板只展示实际执行过的步骤记录，不让模型事后编写“思考过程”。

### 5.2 指标定义

| 指标 | 定义 | 目标 |
|---|---|---|
| NL2SQL 执行准确率（EX） | 执行结果与 gold 结果一致的题数 / 总题数，判定规则见表后说明 | ≥ 90% |
| 鲁棒准确率 | 扰动题上的 EX，同时报告相对原题的下降幅度 | ≥ 85%，下降 ≤ 5 个百分点 |
| 要素链接准确率 | 正确绑定的要素片段数 / 全部要素片段数 | ≥ 90% |
| RAG 检索命中率（Hit@5） | Top-5 片段中包含 gold 证据页或片段的题数比例 | ≥ 90% |
| RAG 答案正确率 | 答案与 gold 一致的比例（LLM 判分 + 人工复核） | ≥ 85% |
| RAG 忠实度 | 答案中每个事实性陈述都能被其引用片段支持的题数比例。LLM 判分后，**人工复核全部 30 题**（题量小，人工最可信） | ≥ 90% |
| 澄清召回率 | 应澄清的题中，实际发起澄清的比例 | ≥ 85% |
| 误澄清率 | 不应澄清的题中，错误发起澄清的比例 | ≤ 10% |
| **澄清交互成功率** | 应澄清的题中，经过澄清后最终答案正确的比例（亮点页要用） | ≥ 80% |
| 多轮条件保持准确率 | 意图状态与期望一致的轮数 / 总轮数；另报“连续正确轮数” | ≥ 90%，每段 ≥ 6 轮 |
| ④ 表召回率 / 精确率 | 预测表集合相对 gold 表集合的召回率和精确率 | 召回率 ≥ 95% |
| ④ 消融收益 | AW 题上 EX（④ 子图）减去 EX（全量 schema），以及 prompt token 降幅 | 报实测值 |
| 端到端延迟 | P50 / P90，按阶段拆分（LLM、DB、检索） | P50 < 8 秒 |

- 比较时忽略列名和列顺序，数值保留 2 位小数。

- SQL 执行失败、超时、误澄清，都算错。

### 5.5 效率测试

**规模**：初赛要求至少 2 种，这里做 3 种，顺带为决赛准备。

- **结构化**：Chinook 原始规模（`invoice_line` 约 2 千行）、×5（约 1 万行）、×45（约 10 万行）。
  - 用 `scale_data.py` 在独立 schema 里复制行（新 ID、日期平移）。
  - 文档里标明这是压测副本。
- **文档**：10 页、100 页两档（由多份 OHR 文档拼成的检索库）。

**方法**：每个规模取同样的 20 道题，每题跑 3 次，从 trace 里取各阶段耗时，报告 P50 / P90。

**要填的表**：

| 规模 | NLU | 要素链接 | 表定位 | SQL 生成 | SQL 执行 | 检索 | 生成答案 | 端到端 P50 / P90 |
|---|---|---|---|---|---|---|---|---|
| 2 千行 | | | | | | | | |
| 1 万行 | | | | | | | | |
| 10 万行 | | | | | | | | |

**复杂度分析要点**（写进说明书第 7 章）：

- **瓶颈在哪**：端到端时间 ≈ 各次 LLM 调用时间之和 + 检索时间 + SQL 执行时间。LLM 调用是秒级；后两者在 10 万行以内是毫秒级。所以**瓶颈在 LLM 调用次数和 prompt 长度，不在数据量**。这一点要用实测数据证明。
- **要素链接**：别名查表 O(1)；模糊匹配 O(V)（V 为候选值数，几千量级）；向量精确检索 O(V·d)。
- **表定位**：向量召回 O((T+C)·d)，T 为表数、C 为列数。Steiner 近似相当于跑 k 次最短路，O(k(|E| + |V| log |V|))；68 张表的规模下是毫秒级。
- **SQL 执行**：带索引的过滤约 O(log n)；聚合扫描 O(n)。用 `EXPLAIN ANALYZE` 给两条代表性 SQL 的实测结果。
- **检索**：BM25 的开销与倒排表长度成正比；向量精确检索 O(N·d)。N 超过 10 万时切换到 HNSW（pgvector），写成扩展路径。

**优化策略**（只写实际做了的）：

- NLU 合并为 1 次调用；
- 单值结果用模板回答；

- 给过滤列加索引；
- 流式输出。

## 附录 B Prompt 要点

**NLU**

```
你是问数/问答系统的意图解析器。只输出 JSON，字段见下方 schema。
- 把用户话里所有可能指向数据库值或业务概念的片段原样抽出到 mentions，
  不要翻译、不要纠错（纠错由后续程序完成）。
- 不确定的字段填 null，不要猜年份、指标或口径。
- 如果是对上一轮的追问，在 patch 里给出相对上一轮意图的修改（set/add/remove），
  不要重写整个意图。
当前会话意图：{intent_json}
可用数据源：{scope}
用户输入：{message}
```

**SQL 生成**

```
根据下面的数据库子结构写一条 PostgreSQL 查询。
只输出 JSON：{"sql": ..., "tables_used": [...], "explanation": "一句话"}。
硬约束：
- 只能使用下列表和列；
- 以下值绑定必须原样使用：{bindings}（例：customer.country = 'Brazil'）；
- 已声明的口径：{assumptions}；
- 只写 SELECT。
数据库结构：{m_schema}
问题（已规范化）：{rewritten_question}
```

**RAG 回答**

```
只根据给出的证据回答。每句话后面用 [E编号] 标出依据。
证据不足以回答时，回答“文档未提供足够依据”，并说明缺什么。
不要使用证据以外的知识。数字必须与证据原文一致。
证据：
[E1] 《文档名》第 3 页 > 章节路径：……
……
问题：{question}
```

-- Top 艺术家（用于挑选跨源知识库的文档）
SELECT ar.name, SUM(il.unit_price * il.quantity) AS revenue
FROM invoice_line il
JOIN track  t  ON il.track_id  = t.track_id
JOIN album  al ON t.album_id   = al.album_id
JOIN artist ar ON al.artist_id = ar.artist_id
GROUP BY ar.name
ORDER BY revenue DESC
LIMIT 10;
