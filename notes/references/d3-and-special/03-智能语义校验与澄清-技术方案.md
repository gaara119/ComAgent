## 1 方案概述

**对于中级③，我建议最终采用“业务元数据约束＋结构化意图表示＋规则校验＋候选解释澄清＋可恢复对话状态”的混合方案。**

| 版本   | 实现路线                                                         |
| ------ | ---------------------------------------------------------------- |
| 第一版 | 规则/有限状态机 + 元数据/RAG + LLM 结构化输出/工具调用的混合模型 |
| 第二版 | 多候选解释、查询探测、信息增益、置信度校准                       |

> **原稿讨论备注：**（多智能体gpt说不适合第一版和第二版，适合第二版后期作为旁路实验）

它不是简单地给大模型加一句“信息不足时请反问”，而是设置一个明确的控制层：

> **问题尚未满足业务查询条件，就不能进入正式查询；能通过数据说明或文档证据补全的信息，系统先自行查证；只有需要用户作出业务选择的信息，才向用户提问。**

## 2 设计原则

**第一，用户意图不确定与模型能力不足必须分开。**用户没有说明“同比还是环比”，需要用户选择；模型不知道两张表如何关联，应先检查schema，不能把技术困难包装成用户的问题。

**第二，澄清候选必须有数据依据。**选项应来自实际存在的指标、字段、文档或业务规则，而不是模型临时编造。

**第三，澄清之后必须重新校验。**用户的回答可能解决一个问题，也可能引入新条件，甚至改变原任务。

**第四，追问也有成本。**应优先询问能消除关键分歧的问题，而不是每次从固定清单第一项开始问。这与结构化不确定性和信息价值方法的方向一致。[相关论文（arXiv）](https://arxiv.org/html/2508.15276v2)

## 4 实现方案

中级③采用一条统一的实现路线：

> **接入赛题指定数据 → 建立业务目录与校验规则 → 用DeepSeek V4.1 Flash理解用户问题 → 检查缺失、歧义与冲突 → 必要时发起澄清 → 更新对话状态 → 将明确后的需求交给查询、检索或计算模块。**

### 4.1 先确定整体架构：模型负责理解，程序负责校验与控制

中级③不能设计成一条独立的提示词，也不能与数据库、文档库和其他模块脱节。建议将它设计为整个问数／问答流程中的**语义检查与澄清模块**。

系统分成两部分。

**公共基础部分**包括数据源、业务目录、模型接入、文档证据和会话存储，供九项中级任务共同使用。

**中级③专用部分**包括必要条件检查、歧义识别、澄清问题选择、用户补充后的状态更新，以及是否允许进入下一步的检查。

#### 采用的组件与分工

| 部分           | 项目选型                               | 在本方案中的职责                                 |
| -------------- | -------------------------------------- | ------------------------------------------------ |
| 用户界面       | Vue 3                                  | 展示对话、澄清选项、当前查询条件和来源依据       |
| 后端接口       | Python＋FastAPI                        | 接收问题、管理会话、连接各功能模块               |
| 主模型         | **DeepSeek V4.1 Flash，即`dpskv4.1f`** | 理解输入、提取条件、提出候选解释、组织澄清措辞   |
| 输出与业务校验 | Pydantic＋自定义规则模块               | 检查输出结构，再检查业务条件是否满足             |
| 流程与状态控制 | LangGraph                              | 组织处理节点，管理等待补充和恢复流程             |
| 系统管理数据   | PostgreSQL                             | 保存业务目录、规则、会话索引、版本与审计记录     |
| 检索部分       | BGE-M3＋pgvector                       | 作为业务描述与文档片段的检索方案，与其他任务共享 |

这是项目的组件安排，不意味着采用这些工具后业务正确性就自动得到保证。

其中，LangGraph的中断与检查点机制可以保存运行状态，等待外部输入，再继续处理；本项目用它承载“暂停查询—等待澄清—恢复任务”的流程。**到底缺少什么、应该问什么，仍由我们设计的业务规则和澄清策略决定。**[LangGraph 官方文档：中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

这一架构的分工可以概括为：

> **模型提出理解结果，业务目录提供依据，规则模块检查是否合法，状态模块保存用户决定，下游模块执行已经明确的任务。**

### 4.2 第一步：接入指定数据，并登记系统实际具备的数据能力

赛题推荐OHR-Bench、Chinook和AdventureWorks（PG）。本项目沿用这三个来源，不另换一套更容易的数据证明功能。[赛题说明](参考资料/赛题说明.pdf)

#### 三个数据来源分别承担什么任务？

| 数据来源                 | 本项目中的使用安排         | 对中级③的作用                                  |
| ------------------------ | -------------------------- | ---------------------------------------------- |
| **Chinook**              | 先建立完整的结构化问数流程 | 验证指标、时间、比较方式、地区口径等澄清       |
| **AdventureWorks（PG）** | 扩展业务概念和复杂关联场景 | 验证新增领域、相近字段、不同业务口径下的澄清   |
| **OHR-Bench**            | 建立文档问答与证据处理流程 | 验证文档对象、期间、公式参数和证据质量相关问题 |

这些是项目分工，不是三套数据天然存在业务关联。

#### 接入时先登记什么？

每个数据源都建立一份“数据能力说明”，至少包含：

| 登记内容                       | 用途                                 |
| ------------------------------ | ------------------------------------ |
| 来源名称、版本、文件或镜像摘要 | 确保后续知道使用的是哪份数据         |
| 实际表、字段、类型、主外键     | 防止模型生成不存在的字段             |
| 业务含义和记录粒度             | 区分一行代表客户、发票还是明细       |
| 数据中出现的日期范围           | 判断用户指定期间是否存在相关数据     |
| 已核验的完整期间及核验依据     | 避免将不完整期间当作完整年度比较     |
| 文档标识、版本和来源位置       | 支撑文档选择及证据追溯               |
| 已知限制                       | 说明哪些指标、业务口径或问题无法支持 |

**“数据中有某个年份的记录”与“该年度数据完整”要分开登记。**不能只查询最大日期，就自动把它解释为“最近完整年度”。

#### Chinook：依据真实字段建立业务口径

Chinook官方PostgreSQL脚本中，客户表存在`country`，发票表存在`billing_country`；发票金额字段是`total`，明细表则包含`unit_price`和`quantity`。这为“客户所在地／账单所在地”等业务区分提供了实际字段基础。[Chinook 官方 PostgreSQL 脚本](https://raw.githubusercontent.com/lerocha/chinook-database/master/ChinookDatabase/DataSources/Chinook_PostgreSql.sql)

据此，我们可以在项目中登记这些指标和维度：

| 项目定义     | 建议绑定                      |
| ------------ | ----------------------------- |
| 发票金额合计 | 在发票粒度汇总`invoice.total` |
| 售出数量     | 汇总`invoice_line.quantity`   |
| 客户所在国家 | `customer.country`            |
| 发票账单国家 | `invoice.billing_country`     |

这些映射必须经过项目审核后生效，**不能由模型每次临时决定**。例如，没有相应定义与数据支持时，不把“发票金额”直接改称“扣除退货后的净销售额”。

#### AdventureWorks：先检查实际版本，再决定覆盖范围

题面指定镜像所对应仓库的README将`postgres`版本描述为AdventureWorks轻量版的PostgreSQL适配，并说明部分视图以及函数、存储过程没有包含。因此，不能只看镜像名称就假定拥有完整企业业务库。[AdventureWorks 镜像项目说明](https://raw.githubusercontent.com/chriseaton/docker-adventureworks/master/README.md)

实施时先固定版本、导出实际schema，再决定用哪些业务问题验证功能。若不足以满足④的“数十张业务表”，应单独处理数据版本问题，不能拿会话表、日志表凑业务表数量。

#### OHR-Bench：原始材料与评测答案分开管理

OHR-Bench的问答数据包含文档来源、问题、答案、证据内容及证据页码等信息。[OHR-Bench 项目仓库](https://github.com/opendatalab/OHR-Bench)

在我们的系统里，应将它们分成两个用途：

**运行侧**使用原始文档及解析结果，完成检索、证据定位和问答。

**评测侧**使用标准答案和标注证据，判断系统是否处理正确。

不能把测试问题对应的标准答案和标准证据直接提供给在线模型，再将结果算作系统自主检索的能力。

同时，不给OHR-Bench文档与Chinook、AdventureWorks虚构客户或企业关系。跨源问题只能建立在已经核验的对象关联或规则关联之上。

**本步骤的产出：三个数据源的登记信息、实际schema、文档清单和能力边界。**

### 4.3 第二步：在原始数据之外，建立全系统共用的业务目录

原始表和文档只能说明“数据在哪里”，还不足以说明：

> 用户说的业务词是什么意思？一个问题必须具备哪些条件？哪些条件已经确认？

因此，建议保留原始业务库，另外建立一个系统管理库。

#### 需要区分的三类数据结构

**原始业务结构**是Chinook、AdventureWorks已有的表字段，以及OHR-Bench的文档内容。

**业务语义结构**是我们补充的概念、指标、字段映射和规则。

**运行状态结构**是用户当前问题、已经确认的条件、待澄清内容和任务版本。

三者不要混在一起，也不要为了适应提示词直接修改原始业务数据。

#### 建议建立的核心记录

下表是项目自定义的数据结构，不是原始数据集自带的表。

| 记录或表                             | 主要内容                                   | 与其他任务的关系 |
| ------------------------------------ | ------------------------------------------ | ---------------- |
| `data_source`                        | 数据源、版本、日期覆盖、能力限制           | 全系统共享       |
| `catalog_object`、`catalog_relation` | 表字段、类型、粒度、关联关系               | 支撑④⑤           |
| `semantic_concept`                   | 业务概念、别名、类型描述、所属领域         | 支撑①②           |
| `concept_binding`                    | 概念与字段、指标、单位、文档定义的映射     | 连接①②③④         |
| `semantic_rule`                      | 必要条件、推导规则、冲突规则、依赖及版本   | ③的核心依据      |
| `document`、`evidence`               | 文档版本、章节、页码、区域、内容和质量状态 | 支撑⑥⑦⑧⑨         |
| `formula_definition`                 | 公式结构、变量、单位、适用条件和证据       | 支撑⑥            |
| `dialogue_session`、`dialogue_event` | 会话索引、用户操作、状态变化、当前版本     | 支撑多轮澄清     |
| `query_plan`                         | 绑定的意图版本、查询或工具计划、运行状态   | 连接④⑤⑥          |
| `audit_event`                        | 实际工具调用、规则命中、耗时和错误         | 支撑解释与评测   |

初版可以先实现最小必要字段，但需要提前确定标识和关联关系。例如：

**业务概念通过`concept_id`关联字段绑定；会话通过`session_id`关联任务；任务通过`intent_version`关联查询计划；证据通过`source_id`和文档版本返回原始材料。**

#### 业务定义不能只保存名称

以一个金额指标为例，建议完整记录：

> 名称是什么，按什么粒度统计，使用哪些字段，按哪种日期筛选，单位是什么，适用范围是什么，定义来自哪里，当前版本是什么。

因此，“销售额”这样的别名只有在当前领域中已被明确登记，才能自动映射到相应指标。存在多个合法口径时，保留候选并交给③处理。

#### 规则也要可以跨领域复用

不要把规则写成：

> 用户说“销售额”，就一定询问年份。

应当写成：

> 当任务涉及时间比较时，需要明确基础指标、当前期间、比较方式和可比口径；已经能够根据有效规则唯一推导的内容，不重复询问。

这样，从Chinook扩展到AdventureWorks时，主要补充业务描述、字段绑定和领域约束，而不是重写整套校验程序。这与②要求的低成本扩展方向相配合。[赛题说明](参考资料/赛题说明.pdf)

**本步骤的产出：业务目录、指标定义、校验规则以及共享证据结构。**

### 4.4 第三步：定义所有模块共同使用的“查询意图记录”

模型不能只返回一句“用户想查询销售额”，因为后续无法判断哪些信息已经明确、哪些是模型猜的。

建议定义统一的**查询意图记录**，也可以称为“查询语义契约”。它的含义很简单：

> **把用户真实需求、尚未确定的条件，以及每个条件的依据，保存成结构化记录。**

#### 记录应包含哪些内容？

| 字段                  | 表示什么                                       |
| --------------------- | ---------------------------------------------- |
| `source_scope`        | 本任务允许使用的数据库和文档范围               |
| `task_type`           | 明细、总量、排名、同比、环比、占比、文档问答等 |
| `entities`            | 查询对象及其标准标识                           |
| `metric`              | 指标标识及定义版本                             |
| `time_scope`          | 当前期间、比较期间、日期口径和必要的日历规则   |
| `filters`、`grouping` | 筛选条件与分组维度                             |
| `formula_ref`         | 涉及的公式及版本                               |
| `unresolved_issues`   | 尚未解决的缺失、歧义和冲突                     |
| `provenance`          | 关键条件来自用户、规则还是文档                 |
| `intent_version`      | 当前需求版本                                   |

每个关键条件还应具有状态，而不只是一个值：

**用户明确提供、用户已确认、有据推导、多候选、缺失、已失效。**

例如，“同比的比较期间”可以根据当前期间和明确的日历规则推导，但要保存推导依据；用户改变期间后，原比较期间应失效并重新推导。

#### 这份记录怎样约束下游？

④⑤⑥应优先使用这份记录，而不是各自重新阅读聊天历史、重新猜测业务含义。

如果⑤发现实际字段可能对应两种日期口径，应把问题返回③处理，不能自行选择后继续生成SQL。

**同一个意图可以对应不同的等价SQL；我们要统一的是业务含义，不是强迫所有查询使用同一种SQL写法。**

**本步骤的产出：统一的意图结构、字段状态和模块输入输出规范。**

### 4.5 第四步：将DeepSeek V4.1 Flash接入意图理解流程

在这一方案中，`dpskv4.1f`统一指你选定的**DeepSeek V4.1 Flash**。模型承担自然语言理解工作，但不单独决定查询是否可以执行。

#### 每次给模型什么信息？

建议输入由四部分组成：

**当前用户输入**，包括新问题或本轮补充。

**当前意图状态**，包括此前已确认的条件和正在等待回答的问题。

**相关业务描述**，只提供检索到的指标、字段、文档说明，不把整个数据库目录全部塞入提示词。

**固定任务约束**，要求模型保留缺失值、输出候选及依据，不擅自补全年份、指标或业务规则。

#### 模型需要输出什么？

模型输出的是一份**意图提取或修改提议**，包括：

| 输出内容     | 示例                                 |
| ------------ | ------------------------------------ |
| 识别到的任务 | 查询同比增长率                       |
| 明确的条件   | 用户指定了某个国家                   |
| 候选解释     | 该国家可能指客户所在地或账单所在地   |
| 缺失信息     | 当前比较年度尚未明确                 |
| 本轮修改     | 把地区条件从原值修改为新值           |
| 对应依据     | 用户原文位置、概念标识或检索证据标识 |

最终的“继续、查证、澄清、停止”由程序综合校验结果决定，不直接采用模型的一句自我判断。

#### 模型输出如何进入系统？

建议经过三层检查：

**结构检查：**字段类型、枚举、标识和格式是否合法。

**对象检查：**模型引用的指标、字段或证据是否真实存在。

**业务检查：**条件是否完整，候选是否有依据，是否与用户已确认的信息冲突。

输出必须允许“未知”“缺失”和多个候选，不能为了填满JSON字段而迫使模型编造值。

#### 模型接入还要保留哪些工程信息？

通过统一适配层保存模型服务配置、实际请求标识、提示词版本、调用时间和错误状态。具体API字段根据实际服务接口配置，不把项目缩写直接写死为接口参数。

结构化输出或工具调用能力也应在接入时验证；不支持时使用文本JSON加本地校验。输出失败只能触发有限重试或明确的技术错误，不能把格式错误包装成“用户需求不清楚”。

**本步骤的产出：模型适配层、固定理解任务模板、结构化输出规范和校验入口。**

---

### 4.6 第五步：用业务规则判断缺失、歧义和冲突

这是中级③的核心。

建议让校验模块依次检查四件事：

> **条件够不够 → 含义是否明确 → 条件是否相互冲突 → 数据和证据能否支持下一步。**

#### 检查一：必要条件是否齐全？

不同任务采用不同规则，不统一要求用户填写所有字段。

| 任务类型     | 主要检查内容                           |
| ------------ | -------------------------------------- |
| 明细查询     | 查询对象、返回内容、必要筛选范围       |
| 总量查询     | 指标、统计范围和必要业务口径           |
| 排名查询     | 排名对象、指标、范围及必要排序要求     |
| 同比／环比   | 基础指标、当前期间、比较规则、可比口径 |
| 占比查询     | 分子、分母及一致的统计范围             |
| 文档公式计算 | 适用公式、参数归属、单位和适用条件     |

用户已经明确，或者能够依据有效规则唯一推导的内容，不应再次追问。

“查询所有客户姓名”不一定需要时间；“查询增长率”则不能在缺少必要比较条件时直接继续。

#### 检查二：是否存在影响答案的多种解释？

候选必须来自业务目录、实际schema或文档证据。

例如，若“美国”既可能对应客户所在地，也可能对应账单所在地，而且上下文没有确定口径，就需要澄清。

但SQL使用子查询还是公共表表达式，通常不是用户需要决定的业务问题。

**即使两个不同口径在当前数据快照上碰巧得到相同结果，也不等于它们在业务上没有区别。**

#### 检查三：是否存在条件冲突？

例如，用户前面选择了一个年度，随后又说“只看另一个年度的第一季度”。系统需要判断这是修改旧条件，还是新增一个对照范围，不能把矛盾条件全部拼进查询。

处理顺序应是：

**明确修改则更新；能够从上下文确定则记录依据；无法确定修改范围时再询问。**

#### 检查四：问题不清楚，还是系统尚未找到证据？

这两种情况必须分开。

| 当前情况                       | 应采取的动作                   |
| ------------------------------ | ------------------------------ |
| 用户未指定关键期间             | 询问用户                       |
| 系统不知道有哪些日期字段       | 检索业务目录或schema           |
| 多个合法日期口径都符合表达     | 向用户提供业务化选项           |
| 公式参数可能位于后续页面       | 继续检索                       |
| 已找到参数位置，但识别质量不足 | 重新解析或提示证据不足         |
| 数据中没有所需业务信息         | 说明数据能力边界               |
| 查询合法但没有匹配记录         | 返回无匹配结果，不擅自修改条件 |

**模型不知道怎么关联表，不等于用户的问题不清楚；文档看不清，也不等于应该让用户替系统补一个数字。**

澄清期间可以进行受限的元数据检查和证据检索，但不能先偷偷选择一种业务解释、计算出结果，再把这个结果当成用户的真实意图。

**本步骤的产出：带原因和依据的校验结果，以及下一步处理动作。**

---

### 4.7 第六步：生成必要的澄清问题，并保存等待状态

发现问题后，不立即把所有缺失字段逐个问一遍。先判断：

> **哪些信息必须由用户决定？哪一次提问最能推动任务继续？**

#### 优先询问什么？

初版建议采用可解释的优先级：

**先处理任务对象和指标，再处理会改变结果的范围与口径，最后处理展示偏好。**

但不固定成机械顺序。两个独立且容易回答的缺失项可以放在同一张澄清卡片上；如果后一个问题依赖前一个选择，就分步询问。

例如：

> **你想比较哪一年的同比？另外，“美国”按客户所在地还是发票账单所在地统计？**

如果用户的问题已经明确指标，就不再额外问“你要查什么指标”。

#### 澄清卡片包含什么？

建议包含问题、简短原因、合法选项和自由补充入口。

用户看到的是“客户所在地／账单所在地”，而不是数据库字段名；字段绑定可以在“查看依据”中展示。

候选选项必须携带稳定的标识。用户点击选项后，系统直接知道选择的是哪个业务概念，不必再让模型解释一次按钮文字。自由文本回答再交给模型解析。

#### 系统暂停时保存什么？

至少保存：

**会话标识、任务标识、意图版本、待解决问题、选项标识、已确认条件，以及澄清请求标识。**

LangGraph提供基于检查点的暂停和恢复机制。恢复可能重新运行发生中断的节点，因此保存事件和创建任务等操作需要避免重复执行；本方案为请求和状态修改设置幂等标识。[LangGraph 官方文档：中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)

等待期间没有用户回答，就保持待处理状态，而不是超时后自行猜测。

**本步骤的产出：澄清卡片及可恢复的任务检查点。**

---

### 4.8 第七步：用户补充后，增量更新状态，而不是重新猜一遍

用户回答后，更新的对象应是已经保存的意图记录。

建议采用：

> **识别本轮改变了什么 → 更新对应条件 → 检查依赖关系 → 使受影响的旧内容失效 → 再次校验。**

#### 哪些条件可以保留，哪些必须重算？

| 用户操作                   | 状态处理                                             |
| -------------------------- | ---------------------------------------------------- |
| “换成加拿大”               | 修改对应地区条件，保留仍然有效的指标和期间           |
| “改查售出数量”             | 修改指标，重新检查单位、聚合方式、数据粒度和查询计划 |
| “上一年也显示出来”         | 增加输出要求，检查是否需要补充结果项                 |
| “刚才的地区不改，只改时间” | 保留地区，仅修改指定期间                             |
| “重新开始，分析另一份报告” | 新建任务范围，不能默认沿用旧业务条件                 |

每次修改都记录修改前值、修改后值、来源轮次和受影响的下游节点。

#### 为什么要有版本号？

假设原需求是“美国发票金额”，用户随后改成“加拿大”。

即使原查询已经在处理中，它返回时也不能覆盖新任务的结果。因此，每个查询计划都要绑定：

**会话、任务、意图版本、业务规则版本和数据版本。**

旧版本结果可以保留用于审计，但不能当作当前答案展示。

#### 状态保存只设一个权威来源

建议以LangGraph持久化检查点保存运行状态，系统管理表保存索引、事件和查询摘要，不再另外维护一份可能不同步的完整对话状态。

同时，前端提交补充时携带澄清请求标识和意图版本，避免用户在旧页面点击选项后误修改新的任务。

**本步骤的产出：更新后的有效意图，以及明确的旧计划失效记录。**

---

### 4.9 第八步：将明确后的需求交给其他模块，并保留二次校验入口

中级③不能只在入口处工作一次。

建议设置两个检查位置。

**第一处在问题理解后：**处理明显的条件缺失、歧义和冲突。

**第二处在数据定位或文档检索后：**处理只有看到实际字段、章节或公式后才出现的业务分歧。

#### 与其他八项任务怎样配合？

| 任务            | 与③的配合方式                                       |
| --------------- | --------------------------------------------------- |
| ①要素识别与改写 | 提供别名候选；③返回用户最终确认的业务对象           |
| ②可扩展要素提取 | 输出通用意图；③使用统一规则检查必要条件             |
| ④Schema Linking | 提供候选字段及业务含义；发现实质歧义时返回③         |
| ⑤多表NL2SQL     | 使用有效意图生成查询；不能自行改变已确认口径        |
| ⑥公式识别与计算 | 提供变量、单位和适用条件；③处理对象或期间归属的歧义 |
| ⑦目录结构识别   | 提供章节上下文和规则适用范围                        |
| ⑧复杂度评估     | 指导需要补充证据时的解析路线                        |
| ⑨质量评估       | 标记关键证据是否可靠，避免不可靠内容被当成确定参数  |

#### 什么条件下允许继续？

放行检查应针对**下一步操作**设置，而不是要求一开始就获得所有最终数值。

例如，期间和指标已明确后，可以进入数据库取数；取数完成、参数和单位核验后，才允许进行公式计算。

建议遵守以下条件：

> 当前步骤所需业务条件已经明确；没有影响该步骤的重大未解决分歧；来源和权限符合要求；计划对应当前有效版本。

这能避免一个循环：必须先拿到计算参数才能查数据库，但参数又只能从数据库取得。

#### 最终如何展示可解释性？

答案旁边展示实际记录：

**用户确认了什么、使用了哪个指标定义、采用哪个期间、调用了哪些工具、SQL或公式是什么、引用了哪些证据。**

这些内容由状态和工具记录生成，不在最后让模型补写一段无法核实的过程。赛题也要求工具调用链、数据来源和溯源展示。[赛题说明](参考资料/赛题说明.pdf)

**本步骤的产出：当前有效的查询／检索／计算计划，以及能够回溯的依据。**

### 4.10 用一个完整例子串起上述做法

下面是设计示例，不是已运行的测试结果。

**前提：**用户已在界面选择Chinook；项目已登记“发票金额”指标；可用期间与日历规则已经核验。为避免假定某个数据版本包含特定年份，将用户选中的年度记为 **Y**。

#### 用户输入

> “美国的发票金额同比增长率是多少？”

系统按以下流程处理：

| 环节     | 具体处理                                                   |
| -------- | ---------------------------------------------------------- |
| 模型提取 | 识别发票金额、同比、美国；保留尚未明确的年度和地区口径     |
| 目录检索 | 查到客户所在地与账单所在地两种合法业务维度                 |
| 规则校验 | 判断当前年度缺失，地区口径存在歧义                         |
| 发起澄清 | 询问需要比较的年度，以及“美国”采用哪一种地区口径           |
| 用户补充 | 在已核验的期间中选择年度Y，并选择账单所在地                |
| 更新状态 | 保存用户选择；按照已登记规则确定比较期间Y−1                |
| 再次校验 | 检查两个期间、指标口径、字段绑定和来源是否满足查询要求     |
| 交给下游 | ④定位字段，⑤生成并校验查询；取数后进行计算与结果核验       |
| 展示结果 | 展示当前条件、结果、查询与计算依据；没有足够数据时说明限制 |

如果用户随后说：

> “换成加拿大，其他不变。”

系统只修改地区条件，使旧查询计划失效，再生成新计划。不重新追问年度、指标和比较方式。

如果用户再说：

> “不看金额了，改看售出数量。”

系统修改指标，重新检查明细粒度、聚合方式和单位；时间与地区只有在仍适用时才保留。

**这个例子中，数据集决定可查内容，业务目录解释字段含义，模型理解语言，校验模块发现问题，对话状态保存选择，下游模块执行明确后的需求。四部分不是独立介绍，而是同一条处理链路。**

## 5 测试与评估

建议分成下面五个层次。

| 测试层次           | 要验证什么                               | 典型例子                                             |
| ------------------ | ---------------------------------------- | ---------------------------------------------------- |
| **功能正确性测试** | 该澄清时是否澄清，不该问时是否直接继续   | 缺少时间时追问；条件完整时不重复追问                 |
| **多轮状态测试**   | 用户补充或修改后，信息能否正确保留与更新 | “换个地区”只改变地区；“改查数量”使原金额计算计划失效 |
| **系统联调测试**   | 澄清结果是否真正传递给④⑤⑥等模块          | 用户确认同比后，下游不能仍按环比计算                 |
| **对照实验**       | 推荐方案是否比简单方案更有效             | 对比“直接生成SQL”“提示模型自行澄清”“完整方案”        |
| **性能与体验评估** | 正确性提高的同时，交互和运行成本是否合理 | 平均追问次数、响应时间、模型调用次数、无谓追问比例   |

其中有一个很重要的区别：

**模块测试看的是“这次澄清动作是否正确”；端到端测试看的是“经过澄清后，最终答案是否符合用户真实需求”。**
