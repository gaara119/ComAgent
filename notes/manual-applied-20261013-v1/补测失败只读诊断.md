# 新版补测失败的只读诊断

审查对象为已保存的真实 DEV 响应与现有程序。**本报告仅诊断，不修改题面、gold、prompt、业务代码或旧运行结果。** 下列边界测试是建议的修复验证清单，尚未由本审查执行，不写成通过。

## sql-38：纯字段 TopN 被误判成缺业务指标

实际记录：[35 题首轮原始回答](../../eval/artifacts/manual-applied-20261013-v1/sql-live-001/responses.jsonl)，按 `id=sql-38` 定位；真实 NLU：[provider 原始响应](../../eval/artifacts/manual-applied-20261013-v1/provider-live/4d7841ba087840c4940d7c196448e687.json)，读取 `response.choices[0].message.content`。

实际请求明确“文件大小已记录”、字节数、前三首、字节数降序及曲目编号并列升序。NLU 原始结果为 `task_type=ranking`、`metric=null`、`rank_object=track`、`top_n=3`、`order={field:bytes,direction:desc}`，并在 `evidence_spans.metric` 保留“字节数”。因此用户并未缺少指标，错误来自系统将直接属性排序套入业务聚合排名的必需条件。

现有 [extractor.py](../../qa_agent/clarify/extractor.py) 有 `explicit_customer_attribute_top`：证明整题是客户属性查询之后，把无业务指标的 `ranking` 转成 `lookup`，保留排序和 N。曲目字段排序没有相同的完整证明分支。随后 [规则](../../qa_agent/clarify/clarify_rules.yaml) 的 `ranking.required=[metric,rank_object]` 与 [RuleEngine](../../qa_agent/clarify/rules.py) 产生 `missing:metric`，返回 L2“请明确要计算的指标”。原始输出没有 SQL，不能拿当前 gold 的执行成功判为该模型输出正确。

另一个可见边界：provider 初次结果的 filters 有 `track.bytes IS NOT NULL`，但 extractor 最后统一用经值链接核对的 `bindings` 替换 filters，而本题没有值链接绑定，故最终语义 filters 为空。不能为了修此题直接放开模型任意 filters；原题完整措辞仍是 SQL 生成依据，修复后须独立核对实际 SQL 是否真正排除 NULL。

**最小程序修复建议：** 仿现有客户属性证明函数，为真实 catalog 上的曲目文件字节属性 TopN 增加完整句法证明。只有整题的对象、属性、排序、条数、投影及其余条件均为纯属性查询，且对应真实字段存在时，才转成 lookup；保留原题、已有条件、N、主要排序和并列规则。不要把 bytes 硬装成销售额指标，不依赖 `sql-38` ID、不写死 Top3 或返回结果，也不改变 system prompt 或 gold。

建议边界测试：

| 用例 | 应检查的边界 |
|---|---|
| 本题原文，模拟 NLU 的 metric 为 NULL | 可证明为 lookup，不再问业务指标；生成 SQL 仍排除未知 bytes。 |
| 相同属性查询换合法 N 或显式升序 | 不依赖 Top3、降序或当前标准结果。 |
| 原文“前3”而 NLU 写 Top10，或原文降序而 NLU 写升序 | 不能通过证明后保留错误 N/方向；应保持未获完整证明状态或由有文字依据的程序校正后再验证。 |
| catalog 没有 track、bytes 或所投影字段 | 不能伪造字段，也不能用特例绕过目录检查。 |
| 属性排序后追加销售额、销量、年份业务限制等未被完整解析的请求 | 不能吞掉新增条件而转成纯 lookup。 |
| 追加未知投影字段、额外排序或未识别尾句 | 完整证明失败，不按一句“字节数”全局免除业务缺口。 |
| 未定义“这批曲目” | 保留 scope_missing，不用全库默认遮蔽范围缺失。 |
| 修改前后题面、gold、prompt 的 SHA | 不变；技术修复不能通过换题或改标准让输出通过。 |

## sp03-03：账单默认已采用，但 L1 的程序标记丢失

真实记录：[sp03-03 首轮](../../eval/artifacts/manual-applied-20261013-v1/special-live-001/cases/sp03-03/turns/000/response.raw.json)，`body` 是已保存的 JSON 字符串，解析后检查 SQL、答案、metadata 和 semantic_contract。

实际 SQL 按 `invoice.billing_country='Brazil'`，同比期间为 2024 相对 2023；答案已经写明“销售额的地区按发票账单国家统计（10月12日已确认默认口径）”。但 `metadata.clarify.level=L0`，`semantic_contract.assumptions` 有这条声明，`semantic_contract.default_assumptions=[]`。因此本问题是默认来源标签没有传递，不能把它诊断成金额口径或地区查询错误。

代码因果链：

1. extractor 程序先清空模型自行生成的 assumptions/default_assumptions，防止模型伪造默认依据，这个约束应保留。
2. `region_gate` 分支采用已批准的 `default_scope=invoice.billing_country`，只把程序声明加入 assumptions，没有加入 default_assumptions。
3. RuleEngine 从 `analysis.default_assumptions` 建立 defaults；这里地区已经设定且 `region_ambiguous=false`，所以不会进入缺地区的程序推导分支。
4. RuleEngine 最终按“有 issues 为 L2，否则有 defaults 为 L1，否则 L0”分类，故已有实际默认声明却输出 L0。

**最小程序修复建议：** 当且仅当程序实际使用已批准地区默认、且用户没有显式指定地区字段时，将同一条有依据的程序声明同时登记为 `default_assumptions`。快路径如也采用 default_scope，应采用同样的来源登记。不要把所有 assumptions 都当成默认，不改 SQL、地区值、已确认业务规则或现有题库标签。

建议边界测试：

| 用例 | 应检查的边界 |
|---|---|
| 2024 年巴西销售额同比 2023 年，无字段口径 | 使用账单国家，说明与 default_assumptions 同步，L1；同比 SQL 不改变。 |
| 明确写“账单国家/账单国” | 显式条件，不能凭本补丁加入默认来源。 |
| 明确写“客户所在地/居住客户” | 保留 customer.country，不移回 billing_country，不标成本账单默认。 |
| 仅说明程序计算过程、最大有记录年份等非缺省信息 | 不能仅因 assumptions 非空就全局标 L1。 |
| 地区默认已用但当前期间仍缺失 | 应保留 L2，而非因 default_assumptions 非空降成 L1。 |
| 正常快速路径的销售额国家查询 | 核对实际采用地区默认时是否也登记来源，不能只修慢路径。 |
| 用户后续明确切换客户所在地 | 显式切换优先，失效及重查按既有多轮流程处理，不能继续声明已被覆盖的账单默认。 |
