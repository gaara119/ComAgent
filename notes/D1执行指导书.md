# 赛题八 D1 执行指导书 A 和 B 分工及 Codex 协作

适用日期：按计划书，D1 为 2026 年 10 月 10 日。A 负责后端和 SQL，B 负责文档检索和前端；用户已明确自己负责 A。

**D1 的交付目标是：同一个界面可以回答一道数据库题和一道指定文档题，展示真实 SQL 或引用原文；两条链路可以通过同一个 API 调用，并产生第一份可复查的评测报告。**

本指导书将计划书 §4.2 的 D1 工作拆成实施步骤，补充请求协议、API 负责人、Windows 环境、数据下载和评测划分。2026-10-10 收口修订已对齐当前 Python 3.12、1 起物理页和用户配置的 Top-K 5；实施步骤用于复现和验收，当前完成情况与实际数字以 system 内的完成记录和本次验收报告为准。根目录原稿与 system/notes/D1执行指导书.md 内容同步。

### 1.2 晚上应该拿到什么

- 一个可以启动的 FastAPI 服务，一个可以打开的 Streamlit 页面。
- Chinook 真实数据、结构目录、只读查询账号。
- 一道中文 SQL 问题得到正确结果，页面能展开查看实际执行的 SQL。
- 一道指定 PDF 的问题得到基于该 PDF 的回答，页面能展开查看原文和物理页码。

EX 指执行准确率，即查询结果与人工确认的标准结果一致的题数比例。D1 不设“必须达到 90%”的硬门槛；计划的 D2 目标才是 SQL EX ≥85%，后续目标是 ≥90%。D1 的数字必须来自实跑。

### 2.4 上午就约定请求和响应

计划书 §3.5 已给出 `Step`、`Evidence`、`IntentContract`、`AnswerEnvelope` 的示意。D1 把它们写成可运行的 Pydantic 模型，并补上请求模型 `ChatRequest`。四个类都保留，避免前端、后端和评测各写一种返回结构。

建议冻结以下请求形式，作为 D1 的新增约定：

```json
{
  "session_id": "d1-demo-01",
  "message": "来自巴西的客户有多少位？",
  "scope": {
    "route": "sql",
    "db_id": "chinook",
    "doc_ids": []
  }
}
```

文档问题将 `route` 改成 `doc`，`db_id` 设为 `null`，`doc_ids` 只放当前选择的一份文档 ID。D1 先由界面显式选择“数据库”或“指定文档”，自动路由按后续计划补齐。

接口约定：`POST /api/chat` 输入 `ChatRequest`，返回 `AnswerEnvelope`。建议另加 `GET /health` 方便检查服务是否启动，这是辅助接口，不改变主业务接口。

响应至少满足：

- 每次请求都有 `trace_id`；无关字段用 `null` 或空列表，不能缺字段。
- SQL 回答包含实际执行的 `sql`、结果 `table` 和实际步骤 `steps`。
- 文档回答包含 `answer`、证据 `evidences`、实际步骤 `steps`。
- `Evidence.page` 存从 1 起的 PDF 物理页，封面计页，界面直接显示，不再加 1；不要混用文档印刷页号。官方 OHR 的 `evidence_page_no` 保留原始 0 起索引，仅转换为内部物理页时加 1。
- 状态沿用计划的五种：`SUCCEEDED`、`EMPTY_RESULT`、`NEEDS_CLARIFICATION`、`UNSUPPORTED`、`FAILED`。
- 缺 key、索引未建、模型输出无法解析或数据库不可连接，归入 `FAILED` 并说明可操作原因；不能伪装成需要用户澄清。
- D1 尚未实现的混合查询或澄清能力，如被请求，应如实返回适当状态，不制造执行成功的记录。

建议 A 提供统一总入口，B 提供文档入口：

```text
pipeline.chat(request) -> AnswerEnvelope       A 维护
SQL 通道(question, scope) -> AnswerEnvelope    A 实现
RAG 通道(question, scope) -> AnswerEnvelope    B 实现
```

两边都使用 `llm.py` 和 `trace.py`。接口样例可以用固定数据开发 UI，但必须明确为演示占位；晚上验收和评测必须换成真实调用结果。

## 3 A 的 D1 实施步骤

A 的工作顺序：Chinook 和模型接入并行准备 → 结构目录 → SQL 最小链路 → API → 题库和 EX → 数据准备结果交给 B。

### 3.1 导入 Chinook 并验证真实数据

**产出：**`docker-compose.yml`、Chinook 导入 SQL、只读角色初始化脚本、数据库检查记录。

1. 从 [Chinook 官方发布页](https://github.com/lerocha/chinook-database/releases)获取 PostgreSQL 脚本，记录发布版本、文件名、下载来源和文件校验值。
2. 在 Compose 中先配置 Chinook PostgreSQL 服务、数据库名、持久化卷和初始化 SQL。D1 不必启动 AdventureWorks。
3. 挂载 SQL 到初始化目录，启动服务，查看日志，确认脚本执行成功。
4. 检查导入后的 schema、表、列、主键和外键。计划示例使用 snake_case，但不同脚本可能使用带双引号的 PascalCase，代码必须跟随实际导入结果。
5. 查客户数、曲目数、发票日期范围和国家实际取值，将结果写入日志。
6. 创建 `qa_reader`，赋予业务 schema 的访问权和表的 SELECT 权；应用只使用该账号查询。管理账号仅用于初始化和标注核验。

以下 SQL 仅适用于实际导入采用 snake_case 命名的情况：

```sql
SELECT COUNT(*) FROM customer;
SELECT COUNT(*) FROM track;
SELECT MIN(invoice_date), MAX(invoice_date) FROM invoice;
SELECT DISTINCT country FROM customer ORDER BY country;
```

**验收：**容器正常、查询返回真实数据、实际日期范围已记录、应用连接串使用只读账号。通过权限信息或非破坏性的验证确认账号不能写入；不能为了测试而修改业务数据。

**常见问题：**初始化脚本通常只在空数据库卷时执行。换了 SQL 后表没有变化，应先查初始化日志和卷状态；不要盲目重复导入或删除已有卷。Windows 的宿主机连接使用映射端口，容器之间连接使用服务名，分别配置。

**Codex 可代做：**下载脚本、生成 Compose 和初始化脚本、启动并查看日志、核对结构和日期范围、生成数据库说明。A 复核实际数据与计划示例是否一致。

### 3.2 验证 DeepSeek 并建立共享调用层

**产出：**`.env.example`、`config.py`、`llm.py`、模型接入检查记录。

你们在本地配置 `LLM_BASE_URL`、`LLM_MODEL`、`LLM_API_KEY` 和 `DB_URL`。不要把 key 发进聊天或打印到日志。

当前 DeepSeek 官方 `/models` 示例将 `deepseek-flash` 对应为 `DeepSeek-V4.1-Flash`。实际接入仍先用你们的账号查询可用模型，再做一次最小调用；模型 ID 放配置，不写死在业务代码中。依据：[DeepSeek 模型列表接口](https://api-docs.deepseek.com/api/list-models/)。

先验证三个问题：

1. 能否成功调用模型，响应对象中能否取出最终内容。
2. 能否返回所需 JSON，并经过 `json.loads` 和 Pydantic 校验。
3. 能否记录总耗时、模型 ID 和接口返回的 token 用量。

`llm.py` 统一完成超时、重试、错误处理和结构校验。建议 JSON 格式失败最多重试 2 次；认证失败、余额不足等问题应直接报告原因。网络重试与格式重试共用总预算，避免嵌套重试导致一次请求反复调用。模型输出为空或被截断也必须视为失败。

SQL 生成输出约定：

```json
{"sql": "SELECT COUNT(*) AS customer_count FROM customer;", "tables_used": ["customer"], "explanation": "统计客户表记录数"}
```

说明：这里的 `explanation` 是简短的查询用途说明，前端实际轨迹来自程序记录。

**验收：**一次真实调用可返回并解析 JSON；错误可被识别；日志中没有 key；B 可以调用同一函数，不需要自己重新接入模型。

**Codex 可代做：**完成配置和调用层、编写模型发现与最小检查脚本、在已配置凭据的环境中执行验证、根据实际错误修复。创建服务账号和充值由你们完成。

### 3.3 导出最小可用的数据库目录

**产出：**`scripts/build_catalog.py`、`data/catalog/chinook.yaml`。

从真实数据库自动读取表、列、类型、主键和外键，再补中文解释和少量示例值。D1 优先核对 `customer`、`invoice`、`track`、`employee`，其余表也应有真实结构记录。

中文解释必须说清容易误用的字段：`invoice.total` 是发票总额，`track.milliseconds` 是曲目时长毫秒值，`track.unit_price` 是曲目单价；客户所在国与发票账单国家是不同列。英文标准值如 `USA`、`Brazil` 和实际员工职位应取自数据库。

SQL prompt 使用紧凑的结构信息，禁止模型猜列名。D1 可以把 Chinook 目录整体交给模型或按显式范围提供已审查表，不把简单表选择宣称为中级④已完成。

**验收：**目录中的表列与数据库一致；日期、金额、国家、NULL 等语义经过 A 核对；目录中不含题目的 gold SQL 或标准答案。

**Codex 可代做：**结构读取、目录生成、中文解释初稿、与数据库结构对照。A 负责语义确认。

### 3.4 实现 NL2SQL v0

**产出：**SQL 生成、校验、执行模块，接入 `pipeline.py`。

最小链路如下：

```text
中文问题和明确的来源范围
  → 根据真实目录生成 SQL JSON
  → SQLGlot 解析和校验
  → 只读执行
  → 按真实结果生成短答案
  → AnswerEnvelope
```

先覆盖计数、筛选、SUM/AVG、分组、Top-N、日期范围、LIKE/ILIKE、NULL 和无匹配。D1 不实现完整别名纠错级联；规范中文问题可借助目录中的标准值。值链接和改写按 D2 实现。

SQL 校验至少做到：

- 只允许一条语句，并检查整个语法树。不能仅检查字符串是否以 SELECT 或 WITH 开头。
- 拒绝写操作、多语句、SELECT INTO、带写操作的 CTE、目录之外的表列及未允许的函数调用。
- 识别真实表名、别名和作用域；聚合函数白名单要覆盖当天题库。`pg_sleep`、`dblink` 等不允许。
- 对没有 LIMIT 的普通列表查询，在外层设置最多 200 行的默认上限；保留用户明确的 Top-N，不改变聚合输入和求和结果。
- 使用只读账号和只读事务，设置 5 秒数据库语句超时；模型调用超时另外管理。

数据库报错后的 SQL 修复最多 2 次，每次修复都重新校验，并保持原问题条件。空结果如实返回；不能把“南极洲”偷偷替换成另一个国家。

`COUNT(*)=0` 是一个成功得到的数值结果；返回零行是空结果；`SUM` 在无匹配时可能为 NULL。三者要区分。一个数值可以直接用模板回答；表格回答先返回原结果，再考虑增加模型总结。

**验收：**至少跑通计数、筛选、排序、日期和无匹配各一题；语法或权限拦截发生在执行前；页面收到的 SQL 与实际执行 SQL 一致。适合做少量有意义的校验边界测试，不需要给每个薄封装写机械测试。

**Codex 可代做：**实现链路、编写边界检查、运行数据库用例、定位并修复 SQL 结构问题。A 核对查询是否忠实于业务问题。

### 3.5 实现 API 和实际步骤记录

**产出：**`api/main.py`、`pipeline.py`、`trace.py`。

这是原 D1 分工需要补齐的工作，由 A 主责。FastAPI 做输入校验、来源分流、调用 SQL/RAG 通道和统一响应；Streamlit 与评测都使用 `/api/chat`，不能各自另走一套链路。

`trace.py` 至少记录 SQL 生成、校验、执行、文档检索和回答的耗时及摘要。D1 不必做复杂可视化，但已有真实记录应能在界面展开。异常也保留已执行步骤；日志和摘要隐藏凭据。

**验收：**使用同一个请求样例可以直接调用 API；正常和失败都能得到统一结构；B 的 RAG 入口接入后无须改变前端响应字段。

**Codex 可代做：**API、路由、计时包装、序列化、接口联调和错误定位。

### 3.6 建立 30 道 SQL 题并生成 EX 基线

**产出：**`eval/datasets/nl2sql_chinook.jsonl`、gold 结果、`eval/run_eval.py`、`eval/metrics.py`、开发集报告。

建议 30 题分配如下：计数 3、筛选 5、求和/平均 4、分组 4、排序 Top-N 4、日期 3、模糊匹配 2、NULL 3、无匹配 2。每题只涉及一张真实业务表，不把“按流派中文名查歌曲”这种需要 JOIN 的题混入单表基线。

每题至少包含：`id`、`question`、`gold_sql`、`gold_result`、`category`、`ordered`、`split`。日期题先查询实际年份，再填写年份，不保留 Y 占位符。

执行顺序：

1. Codex 起草题目及 gold SQL，A 按业务含义逐题审查。
2. 运行全部 gold SQL，核对结果并保存。运行 gold 是标注核验，不等于对保留题运行系统预测。
3. 按题型分层固定 21 道开发题、9 道保留题；预先写好标记。后续扩到 50 题时继续维持约 30% 保留，并保持同源题归组。
4. D1 自动评测只调用 21 道开发题的 `/api/chat`。9 道保留题按计划 D5 冻结后才评测，不用于调 prompt。
5. 报告保存每题请求、响应、执行结果、判定、错误类型和耗时；注明 Git commit、数据版本、模型 ID 和题目分母。

结果比较沿用计划 §5.2：忽略列名和列排列差异，有序题比较行序，无序题比较多重集合，不能丢掉重复行。列排列要做全局一致的对应，不能把每一行各自排序。日期和 Decimal 做一致的序列化；金额按计划统一到 2 位小数，同时保留原始结果，整数和 NULL 保持原义。

Top-N 题要提前约定并列处理；必要时题目声明第二排序键，防止相同问题出现多种合法行序。执行失败、超时、格式错误、误澄清都计入分母并判错。

报告格式可以是 `正确 x/21，EX=x÷21，失败分类……`。不要把“SQL 可以执行”当成结果正确，也不要把 21 道开发题的成绩写成全体 30 题成绩。

**验收：**30 题 gold 已审查；开发集报告可复跑；保留集没有系统预测记录；Gold 不进入业务 prompt、目录或运行知识库。

**Codex 可代做：**题库草案、gold 执行与导出、分层划分、评测代码、报告和错误分析。A 最终确认 gold 的业务意义，不能只看模型自己判自己正确。

### 3.7 给 B 提供跨源资料准备信息

按计划附录 C 运行 Top 艺术家销售额查询，并检查客户国家和账单国家是否确实存在差异。

给 B 一份真实查询结果：艺术家英文名、排序、销售额、取数时间和 SQL。B 据此准备后续百科资料，不能预先把某个示例乐队当成实际冠军。

这条多表 SQL 是人工确定的数据准备脚本；它不表示 D1 已实现多表 NL2SQL、中级⑤或跨源问答。D1 先把名单交接清楚，页面跨源能力按后续计划实现。

**Codex 可代做：**执行已确认的查询、导出结果、整理交接清单。A 复核销售额口径。

## 4 B 的 D1 实施步骤

B 的工作顺序：资料下载和模型准备并行启动 → 选文档与题目 → 逐页解析切片 → 指定文档检索 → 证据回答 → Streamlit 接 API → 开发集核验。

### 4.1 获取 OHR 并选择 6 份文档

**产出：**原始 PDF、原始 QA、`data/docs/manifest.csv`、语言盘点。

先获取 QA 并筛候选，PDF 下载同时启动。需要的来源是原始 PDF 和 QA；D1 不必下载全部 OCR 扰动数据、全部 OCR 模型或整套官方评测环境。

官方资料入口：

- [OHR-Bench 官方仓库](https://github.com/opendatalab/OHR-Bench)。
- [官方 QA JSON](https://raw.githubusercontent.com/opendatalab/OHR-Bench/main/data/qas_v2.json)。
- [官方 Hugging Face 文件列表](https://huggingface.co/datasets/opendatalab/OHR-Bench/tree/main)。

当前 HF 列表中的 `pdfs.zip` 约 1.52 GB。计划附录的下载命令是示意：当前 QA 的官方 GitHub 路径是 `data/qas_v2.json`，HF 根目录没有同名独立 JSON，不能只靠 HF 的 include 匹配保证下载到它。让下载脚本先检查实际文件树，并记录下载版本。

按计划选金融、法律、教材、手册、新闻、学术各 1 份。QA 中相应领域通常用 `finance`、`law`、`textbook`、`manual`、`news`、`academic`；注意新闻字段是 `news`。

优先选择：原生 PDF 可提取正常文本、每份能提供约 3–4 道清晰的文本证据题、证据主要在单页或少量连续页、长度适中。先在 QA 中挑候选，再打开 PDF 检查质量，不能因为有 QA 标注就认定 PDF 解析无问题。

清单至少记录：

```text
doc_id,title,path,qa_doc_name,domain,language,format,source_url,
license_note,sha256,page_count,parse_status
```

`qa_doc_name`、稳定的 `doc_id` 与真实 PDF 路径必须一一对应。保留原始文件，处理结果另存。语言逐份抽查：英文题保持英文原题基线；用于中文演示的译题另外保存并人工确认，不能把翻译过的题冒充原始题。

许可记录以实际声明为准：HF 元数据标为 CC-BY-4.0，官方仓库 README 另有研究、非商业用途的版权说明；这些信息不自动覆盖每份第三方 PDF 的分发权。保留声明、来源及最终样本分发所需信息。依据：[数据集说明](https://huggingface.co/datasets/opendatalab/OHR-Bench/blob/main/README.md)、[官方版权说明](https://github.com/opendatalab/OHR-Bench#copyright-statement)。

**验收：**清单中的 6 份 PDF 都真实存在、能打开、来源和语言清楚；QA 可以关联到正确文件。D1 不把这 6 份 PDF 写成“已满足最终不少于 10 份不同格式文档”。

**止损：**60–90 分钟仍没有一份可用 OHR PDF，就先用已有的合法文本 PDF 开发解析和页面，继续下载 OHR。记录为临时开发语料；OHR 六份文档和 20 题任务仍列为未完成，不能替换后宣布已完成原定验收。

**Codex 可代做：**检查文件树、下载和解压、按 QA 字段筛候选、生成来源清单初稿、统计语言和页数。B 选择最终文档并检查原页。

### 4.2 选择并核对 20 道 RAG 题

**产出：**`eval/datasets/rag_single.jsonl`，与原始 QA 的 ID 映射和核验记录。

只选 `evidence_source = text` 的问题，D1 优先短事实、明确对象和简单数字题。表格恢复、公式计算、复杂跨页问题放在后续题清单中。

当前 QA 存在以下类型差异，转换脚本必须处理：

| 字段 | 处理要求 |
| --- | --- |
| questions、answers | 当前可为字符串，不能因字段名为复数就当成列表 |
| evidence_context | 可能为字符串或列表；保留原值，另规范化为 gold_contexts 列表 |
| evidence_page_no | 可能为整数或列表；保留原值，另规范化为 gold_pages 列表 |
| doc_name | 含领域的路径式名称，必须映射到实际 PDF |

这些字段来自 [官方 QA JSON](https://raw.githubusercontent.com/opendatalab/OHR-Bench/main/data/qas_v2.json) 的实际样本。`evidence_page_no` 采用原始 0 起索引，原值保留；转换到内部 `physical_pages` 和 `Evidence.page` 时仅加 1 一次，并对照实际 PDF 核验。打印在页面上的页号单独处理，前端直接展示内部物理页。

建议先选 25–30 道候选，由 B 对照 PDF 核对后保留 20 道，六个领域均覆盖。每题保存：原始 ID、`doc_id`、原题、可选中文译题、标准答案、标准证据、标准页码、领域、`split`、人工核验状态。

按计划的保留集纪律固定 **14 道开发题、6 道保留题**。B 可以核对全部标注；D1 系统预测和调试只用开发题，保留题到 D5 冻结后再跑。后续扩到 30 题时保持分组规则，同源原题和翻译、扰动变体归同一组。

严格区分三类内容：

| 目录用途 | 内容 | 问答服务是否可读取 |
| --- | --- | --- |
| 原始知识库 | PDF 与来源清单 | 可以 |
| 运行索引 | 从原 PDF 提取的文本、片段、向量、关键词索引 | 可以 |
| 评测标注 | 问题、标准答案、标准证据与标准页码 | 不能作为运行时依据 |

评测脚本发给 `/api/chat` 的只有用户问题、来源范围和会话信息。gold 答案、gold 片段和 gold 页码在收到系统输出后才用于比较。尤其不能把 QA 的 `evidence_context` 导进检索库，或按 gold 页码限制检索，这会泄露答案。

**验收：**20 道标注可回到原文验证；页码映射明确；14/6 划分已固定；问答服务和索引构建流程均不读取 gold。

**Codex 可代做：**字段适配、筛选、格式转换、划分和核验位置清单。B 人工确认答案与原文。

### 4.3 实现 PDF 逐页解析和切片

**产出：**`qa_agent/rag/parsers.py`、`chunker.py`、`scripts/ingest_docs.py`、可追溯片段文件。

D1 先支持原生 PDF。用 PyMuPDF 按页提取文本块，并保留 `doc_id`、物理页索引、文字和位置。每份文档统计页数、提取字符数、片段数和异常页。

切片初始沿用计划的约 400–600 字符、重叠约 80 字符，并写成配置。优先保持段落完整；英文记录所用预算单位，后续根据召回结果调节。

每片至少有：稳定的 `chunk_id`、文档 ID、标题、从 1 起的 PDF 物理页、原文、章节路径和可用的 bbox。D1 不跨物理页切片，以便一个 `page` 能准确定位；底层 PDF 库的 0 起页索引只在解析入口转换一次。

标题能可靠识别才写入 `section_path`，否则为空。bbox 没有可靠坐标时允许为空，不能让模型编造。扫描页、乱码页或双栏读序混乱的页面登记异常；完整 OCR 和复杂目录恢复按后续计划实现。

**验收：**每份文档至少抽查 2 个片段，按页码回到原 PDF 能找到原文；没有把 QA 标准证据当成解析文本；空页不会被默默算成解析成功。

**Codex 可代做：**解析器、切片器、统计与抽查清单。B 查看原页，确认提取质量。

### 4.4 建立指定文档检索和证据回答

**产出：**`index.py`、`retriever.py`、`answer.py`、离线索引和 RAG 入口。

先建 BM25 检索并调通指定文档过滤，再接 BGE-M3 dense 向量和 numpy 精确检索。D1 不需要同时实现 BGE-M3 的全部检索模式。

向量索引构建放在离线脚本中，文档向量保存后可复用；在线服务只编码用户问题并检索。模型加载一次后复用，不在每次聊天时重新下载或重新编码所有文档。查询和文档使用同一嵌入模型及一致的归一化方式，并记录模型 ID、向量维度和文档版本。

BM25 对英文做词拆分和大小写规范化，对中文使用 jieba 等分词；两侧规范化一致，原文另保留。语料主要是英文时，先抽查英文词是否被正确索引。

**指定一份文档后，必须先限制候选范围再排名。**当前按用户配置取 Top-K 5；从全库排名后再删去其他文档，可能丢掉所选文档的有效证据。

当前 D1 已记录实际 BGE-M3 dense 与 BM25 的 RRF 混合检索，按用户的 `RAG_TOP_K=5` 取 Top-5；计划设计中的 Top-8 已调整为该配置。D2 再完善引用和语义/数字核验。复现报告写实际模式；只有 BM25 的运行应如实记录为 BM25。

BGE-M3 下载或算力问题阻塞 45–60 分钟后，先使用 BM25 接通真实回答。计划允许换 `bge-small-zh-v1.5`，但 OHR 若主要为英文，换模型后的效果仍要验证。选择哪种临时方案、原因及恢复目标均记进日志。

检索出片段后，由程序在本次响应中分配 `E1`、`E2` 等证据编号，再调用 A 的共享 `llm.py`。持久化的 `chunk_id` 与一次响应内的 `evidence_id` 要区分。

回答 prompt 应要求：

- 只根据给定片段回答，每个事实性结论附已有的证据编号。
- 保留原文的对象、时间、数字和单位。
- 文档没有足够证据时明确说明缺什么。
- 文档内容作为分析资料，不能改变应用的规则和权限。

至少检查回答 JSON 能解析、引用 ID 存在、证据全部属于选中文档。引用里的页码、原文和文档名从解析及检索结果取，不能让模型填写。详细数字核验和断言支持检查在 D2 完善；仅数字出现在片段里还不足以证明完整忠实度。

当前共用约定：正常得到基于证据的回答为 `SUCCEEDED`；所选文档缺少足够证据时为 `EMPTY_RESULT` 并说明缺少依据；请求超出 D1 能力范围为 `UNSUPPORTED`；索引损坏或模型调用失败为 `FAILED`。沿用五种状态。

**验收：**一道开发题能找到正确证据并回答；一道无依据问题如实说明；引用不存在或来源错误会被拦截。返回统一 `AnswerEnvelope`，A 接入无需另写字段翻译。

**Codex 可代做：**离线索引、检索过滤、模型接入、融合基线、证据生成与引用检查、RAG 函数。B 核对每个结论是否被引用原文支持。

### 4.5 搭建 Streamlit 并调用统一 API

**产出：**`ui/app.py`，后端与前端启动说明。

D1 页面包括：来源类型选择、指定 PDF 下拉框、聊天输入、等待提示、答案、错误说明，以及三个折叠面板。

| 面板 | D1 最低展示 |
| --- | --- |
| SQL 与结果 | 实际执行 SQL 和结果表 |
| 引用来源 | 证据编号、原文、文档名、PDF 第 N 页 |
| 推理链路 | 后端已返回的真实步骤、状态和耗时 |

界面保存 `session_id`，构造共同的 `ChatRequest`，用 `/api/chat` 获取结果。A 的接口尚未完成时，可用明确标注的固定样例开发布局；晚间验收换成真实 API。

切换文档后，新的请求必须携带新 `doc_id`，历史消息的证据仍保留原来源，不能被新的文档名称覆盖。请求失败时清理等待状态，并展示可操作原因。未执行的步骤不显示为成功。

PDF 页面高亮属于计划 P2；D1 先保证原文和正确页码能定位。漂亮布局、澄清卡片、多轮状态和完整看板不应阻塞当晚联调。

**验收：**UI 可以提交一道 SQL 题和一道指定文档题，两题都走真实 API；SQL、结果、引用与该响应一致。

**Codex 可代做：**Streamlit 页面、HTTP 接入、加载与异常状态、响应面板。B 实际打开页面检查交互和来源展示。

### 4.6 运行 RAG 开发集并人工核验

**产出：**14 道开发题的逐题响应、检索记录和人工核验表。

复用 A 的评测入口。每题保存问题、`doc_id`、状态、答案、引用、按实际配置检索的 Top-5 片段、页码、检索耗时、生成耗时和端到端耗时。离线解析、索引构建、首次模型加载和在线热请求耗时分别记录。

B 对这 14 道开发题逐题检查两个不同问题：答案是否回答了原题；每个事实性结论是否被它引用的原文支持。答案看着合理但原文没有支撑，忠实度仍不通过。

可以同时记录 Top-5 的 gold 页码命中作为 D1 定位指标，但明确写“证据页命中 Hit@5”。同页命中不等于准确找到目标片段；人工进一步核对原文内容。不要把页码命中、答案正确和忠实度混成同一个指标。

报告写清正确数/14、证据支持数/14、失败原因和人工审核状态；6 道保留题保持未运行。D1 若暂未完成某项审核，单独注明，不能用模型自评分填成已核验成绩。

**Codex 可代做：**批量运行、保存响应、生成核验表、页码命中计算、定位失败题。B 负责原文支持关系的人工判断。

## 8 卡住时如何处理

| 问题 | 当天处理 | 必须记录的限制 |
| --- | --- | --- |
| Docker 引擎不可连接 | 启动 Desktop，查引擎、Linux containers 与具体错误；先写独立模块和题库草稿 | 未能访问真实库时，SQL 端到端仍未完成 |
| Python 依赖冲突 | 使用统一版本的独立虚拟环境，按具体包错误解决 | 记录两台电脑实际版本，别把全局环境当项目环境 |
| API 认证或余额问题 | 人处理 key、额度；Codex继续做解析、校验、UI样例 | 固定样例不能算真实模型调用 |
| OHR 下载耗时 | 下载后台继续，用临时真实 PDF推进代码 | OHR 六份/20题未齐就保留未完成标记 |
| BGE 下载或运行过慢 | 先用 BM25 接通，按计划尝试较小模型 | 记录实际模式，D2补向量验证 |
| PDF 乱码或扫描页 | 换清晰原生候选，异常页登记，OCR按后续计划 | 不声称已支持扫描件和复杂版面 |
| SQL 答案错误 | 按值、表列、条件、聚合、格式分类修；保留失败记录 | 不删失败题、不扩大分母外的成功率 |
| RAG 答非所问 | 先检查 doc_id、解析、切片和召回，再查生成 prompt | 不能用 gold 片段补进运行索引 |
| A/B 字段不一致 | 回到共同请求/响应模型，修一处协议并同步 | 不在前端长期维护另一套兼容字段 |
| 时间不足 | 先两条真实链路和证据，再评测与资料补齐；美化延后 | 未完成题数与资料任务明确列入 D2 |
